# 前端原型还原：PDF 视觉与资源门禁

适用于**所有前端页面**：志愿者端微信小程序、现有后台管理控制台，以及将来开工的独立监管后台。新建页面、重做布局、增删入口或调整图标前都必须过这道门禁；只改文案或修纯逻辑时也不能借旧记忆改动无关视觉。

本页只规定原型怎么看、资源怎么取、差异怎么留证。小程序的色调与组件见[小程序页面构建](小程序页面构建.md)，现有后台见[后台页面构建](后台页面构建.md)，监管后台的开工边界见[领域十二](../领域/12-监管后台.md)。

## 1. 先确认业务，再确认画面

1. 先读对应领域页的现行规则、功能状态、`知识库/决策/协会决策.md` 与需求表，找到 Row；再用 `知识库/需求/原型.md` 的页标题定位 PDF 页码。
2. 打开需求原件 `文档/志愿平台设想【第十版】.pdf`，把对应页**渲染成图片并实际查看**。必须看到页面整体、相邻元素、选中态与批注；只读提取文字、只看 PDF 目录或凭记忆描述都不算完成核对。
3. 一页有多个界面或状态时要分别看清，不因它们挤在同一 PDF 页就漏掉。临时渲染图放工作区的临时目录，不混入正式发布包，也不把原型中的真实信息带进公开知识库。
4. 在编码前列出本页最小对照：Row / PDF 页码、页面区块、按钮与选中态、图片和图标来源、将复用的现有组件。实现记录须能追溯到这些来源。

**优先级不变**：代码 > 知识库现行要点 > 按批次的记录 > 原型与规划。原型与最新协会口径、现行代码冲突时，先登记差异并按现行规则实现，不能用旧原型恢复“待审核”等已被推翻的流程。视觉缺失可以补设计，业务规则不能自行发明。

## 2. 图标与图片必须来自可说明的来源

按以下顺序处理，不能一开始就凭截图重画或用相近图标代替：

1. **内嵌原图优先**：用 `pypdf` 等读取该 PDF 页的资源与 XObject，找到页面实际引用的独立图片再导出。记录原资源名，并核对它在页面中的位置，不能把同页另一张图当成目标图标。
2. **页面裁剪兜底**：PDF 没有可独立提取的原图、资源组合无法直接还原时，才把该页高分辨率渲染后按实际边界裁剪。记录 PDF 页码与裁剪依据；不确定边界时保留完整区域再核对，不截掉相邻内容。
3. **保留原貌**：保留原色、透明通道和宽高比；不随意改色、拉伸或重绘。展示时用既有尺寸和 `aspectFit` 等等比方式，点击热区由外层按钮承担。
4. **复用要明说**：已有资源确实同族可复用时，登记“复用哪个既有文件、用于哪个原型位置”，不虚构“本页新下载”。新图标写入对应前端的资产目录和提取脚本，使用新增路径或独占创建，避免覆盖无关资源。
5. **确无原型资源才新增设计**：标注为新增设计及原因，不归入“原型同款”。业务图片、商品封面、用户头像和规则正文来自真实接口，不用 PDF 示例数据冒充线上内容。

每个新增或复用的图形至少留下：**原型页码、原资源名／裁剪依据、目标路径、复用关系**。脚本里的 PDF 路径、页码和坐标只对当时那份原件有效；再次运行前必须核对，不能当任意页面通用命令批量覆盖。

## 3. 各端怎样落地

### 3.1 微信小程序

- 先归组再取色：通用页面、首页／“我的”、公益捐赠分包各有现行色板，不从单张截图另取一套颜色覆盖全站。
- 四件套、路由、导航、安全区、四态、分页、防重与接口规范化按[小程序页面构建](小程序页面构建.md)执行。PDF 中没有的独立入口图标，不为了“凑齐原型”自行造一组。
- 商城 P29–P34 已按上述方式实际核对：P29 是姓名、积分、卡卷、八入口和双列商品；P30 是评价，P31 含积分明细与我的兑换，P32–P33 是卡卷状态，P34 是商品详情与评价。共享头部为 `components/mall-header`，八入口使用文字边框按钮，当前项为红色文字和边框；协会标志复用既有 `assets/icons/activity-logo.png`，本批没有臆造八个入口图标。商品图及业务数据仍由接口提供。
- “赚取积分”进入志愿活动列表；商品详情不套共享头部。上述是本批页面接线事实，不是其他分包可以照搬的通用导航。
- 对照 P29 / P31 复查后，共享头部使用四列两行完整展示八个入口，卡卷独立限宽；“我的兑换”不额外发明竖排状态筛选，订单卡展示订单编号、商品名、规格、赞助商家、积分、状态、领取方式及评价状态，整卡进入详情。评价状态只读，不据此新增评价或订单写操作。
- 对照 P32 / P33，卡卷页的“可使用／已使用／已过期”必须各占整行三分之一，文字在各自格内居中，当前项保留红色文字与下划线。八入口仍占四列，单元格横向内边距为 14rpx，以收窄边框并略增间距；卡卷框宽 104rpx，窄屏为 96rpx。三态切换已真机复验，其余页面的验证范围见[回归验证](../回归验证.md)。

### 3.2 现有后台管理控制台

- 新建或改结构前同样先渲染并查看对应 PDF 页，再归入现有 Ant Design v5 风格；不能因后台已有一套页面就跳过原型核对。
- 色调、表格、抽屉、权限、脚本注册与真实接口验收按[后台页面构建](后台页面构建.md)。保留本地 `Icon` SVG 体系，不把小程序 PNG 直接搬进后台。
- 原型给出了对应图标或品牌资源时，先按第 2 节核对原始来源及能否复用；确需补进 `ICONS` 时仍登记来源，并保持现有 24×24 坐标与描边风格。原型未提供时才能按现有语义图标体系选择。

### 3.3 将来的独立监管后台

- 开工前同样执行本页门禁，并先满足[领域十二](../领域/12-监管后台.md)的独立应用、独立库与登录态等边界；不能为了复用页面把它塞进现有单组织控制台。
- Row 82–Row 86 没有对应视觉页时，必须在实现记录中写明“原型缺口”和已确认的设计依据，再开始页面设计；不虚构 PDF 页码或图标来源。
- 技术栈、组件与权限契约一经确定，应补到它自己的页面构建页；本页只提供共同门禁，不预先宣称这些能力已经实现。

## 4. 交付前核对

- [ ] 已定位 Row 与 PDF 页码，渲染图已实际查看，而非只读文字索引。
- [ ] 页面结构、入口顺序、选中态、色板与原型或现行页面组一致；差异有理由和记录。
- [ ] 图标优先提取内嵌原图，裁剪／复用／新增设计的来源均已登记，比例、透明通道和原色未被破坏。
- [ ] 业务示例没有被写成真实数据；原型旧状态没有推翻最新协会口径或代码。
- [ ] 静态检查、逻辑测试、原生／浏览器视觉、真实接口和写流程分别验收；未验项单独列出，不用 mock 或编译成功代替。
