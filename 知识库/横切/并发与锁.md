# 并发与锁

> 全项目反复撞到的并发形状。各模块页里有具体落点；这里是通用规则。
> 2026-10-17 从《约定与踩坑》按主题拆出；一条一节，先说规则、再说为什么 / 撞过什么。

## 分布式锁一律走 `DistributedLockSupport`，锁在事务外取

**分布式锁复用 common `DistributedLockSupport`**：新增 Redisson 锁勿各自手写获取/释放，调 `runLocked`/`runLockedMany` 并自带 key 前缀（现有 `lock:enroll:volunteer:`/`lock:group:volunteer:`/`lock:point:volunteer:`/`lock:honor:ranking-snapshot:`/`lock:coupon-grant:request:`/`lock:pair:register:`/`lock:complaint:volunteer:`/`lock:address:volunteer:`/`lock:org-structure`（全局一把）/`lock:social:volunteer:`/`lock:social:interaction-digest`（全局一把）/`lock:temp-leader:volunteer:`/`lock:enterprise:points:`，互不抢占）。**「幂等键 + 唯一键」不能代替锁的一种情形**（卷批压测撞出来的）：同一幂等键的并发重放若都读在首个写入者提交之前的快照上，会逐行撞唯一键，而撞键失败的 INSERT 会在 PRIMARY supremum 上留下间隙锁，两个重放的下一次 INSERT 在同一间隙上互等成死锁——批量写入按幂等键上锁（锁在事务外），见 `MallCouponService.grant`。

## CAS 失败之后的复核读必须是当前读

只要事务里此前做过任何普通读，RR 的读视图就已定死，CAS 输家用普通读复核会看到赢家提交之前的旧状态，于是报出错误的提示（「只有核对合格的才能生成（当前：合格）」这类）。复核用 `selectByIdForShare` 一类的当前读；撞唯一键之后取回赢家同理，且用 `FOR SHARE` 不用 `FOR UPDATE`——InnoDB 报重复键时已给冲突行加了 S 锁，多个输家再抢 X 会互等成死锁（`PointRecordLockOrderTest` 确定性复现）。落点见 donate（捐书生成专属码、核销员核销）、honor（证书撞键）、activity（积分入账）三个模块页。

## 别对可能还不存在的行加锁或做范围 UPDATE

**别对一个可能还不存在的人的行做范围 UPDATE / 当前读（2026-09-17 考试批又撞一次）**：`WHERE volunteer_id = ?` 在二级索引上命中零行时留下的是**间隙锁**，两个 id 相邻的人各持同一段间隙、再各自 INSERT 取插入意向锁，互等成死锁——与结对批登记同形。先普通读找出要改的行、再按主键改（前提是这个人的写入已被别的锁串行）。**按人的 Redisson 锁帮不上忙**：冲突发生在不同的人之间。

## `AFTER_COMMIT` 监听里写库用 `REQUIRES_NEW`；高并发入口改为事务外发布

**`@TransactionalEventListener(AFTER_COMMIT)` 里要写库，用 `PROPAGATION_REQUIRES_NEW`**（商城快递批的 `MallOrderService.onPaid`）：回调运行时外层事务已提交、资源仍绑在线程上，默认 REQUIRED 会加入那个已提交的事务——写进去的东西要靠连接归还时 autocommit 复位的隐式提交才落库，碰巧成立不等于正确。⚠️ **但这样一个线程同时占两条连接**（外层那条还没还，REQUIRES_NEW 又要一条）——挂在**高并发入口**（付款回调）上时，并发数一到连接池大小整池卡死（捐款批压测撞出）。高并发的发布方改为**在事务之外发布**、订阅方加 `fallbackExecution = true`（见 trade 行）；两个证书监听器挂在后台人工操作上，仍是原写法。**这类缺陷别靠并发去撞**：把连接池限成 1 条（`spring.datasource.hikari.maximum-pool-size=1` + 短 `connection-timeout`），单线程就能确定性复现，见 `PaymentListenerConnectionTest`。
