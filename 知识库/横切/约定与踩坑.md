# 跨模块约定与踩坑

> 由根 `CLAUDE.md` 的「注意」一节下沉而来（2026-10-17）。根文件只留了最硬的几条一句话版本，这里是完整说明。
> 之后会按主题拆成单独的横切页（积分账本、证书、处置闸门、通知短信、收付、上传、并发与锁、测试纪律、迁移、部署）。

- Design Docs 列出的设计文档已统一为**领域垂直切分**口径，模块边界与本文件一致；如个别处仍有出入，**以本文件为准**。
- 写 Controller 前必须先查阅 `文档/v1/url文档v1.md`（见「接口 URL 约定」节）。
- **状态/角色魔法数已收敛到 `constant` 持有类**（单一来源、零行为变化）：跨服务复用的码集中在各模块 `constant` 包——activity 的 `ActivityStatus`（含发布态 4/5 与 `isUnderReview`）/`EnrollmentStatus`/`AttendStatus`/`RunStatus`/`SecretaryStatus`/`PointsStatus`/`PointsFactor`/`LeaderType`/`AuditStatus`，organization 的 `MemberStatus`/`MemberRole`/`GroupStatus`/`SquadApplyStatus`；service 引用持有类常量而非自定义私有魔法数。仅单服务自用的语义码（`CheckInMethod`/`ViolationType`/`ChangeType`/`OpType`/`SquadEnabled` 等）保持就地定义。新增状态判断时优先复用/扩展持有类，勿重新散落魔法数。
- **通知短信只走 auth 的 `SmsNotifyService`**：新增通知场景时，先在 common 的 `SmsNotifyTemplate` 里登记（模板键 + 变量名 + **顺序**，并在 javadoc 写清落点），再在业务侧 `TPL.params(...)` 按序传值——**不要在业务代码里手拼 `Map` 或直接调 `SmsService.send`**：前者会把「变量名拼错」这类无征兆缺陷放回来，后者绕过了「等事务提交、异步派发、失败不影响业务」三条纪律。模板 ID 配在 `hengde.sms.templates.<键>`，生产走 `部署/api.env.example` 里的 `SMS_TPL_*` 环境变量（⚠️ 那是 systemd 的 `EnvironmentFile`，**值后面不能跟行尾注释**）。配了模板却没人调用是无害的；反过来，接了业务却漏配模板，启动时会 warn 列出来。
- **分布式锁复用 common `DistributedLockSupport`**：新增 Redisson 锁勿各自手写获取/释放，调 `runLocked`/`runLockedMany` 并自带 key 前缀（现有 `lock:enroll:volunteer:`/`lock:group:volunteer:`/`lock:point:volunteer:`/`lock:honor:ranking-snapshot:`/`lock:coupon-grant:request:`/`lock:pair:register:`/`lock:complaint:volunteer:`/`lock:address:volunteer:`/`lock:org-structure`（全局一把）/`lock:social:volunteer:`/`lock:social:interaction-digest`（全局一把）/`lock:temp-leader:volunteer:`/`lock:enterprise:points:`，互不抢占）。**「幂等键 + 唯一键」不能代替锁的一种情形**（卷批压测撞出来的）：同一幂等键的并发重放若都读在首个写入者提交之前的快照上，会逐行撞唯一键，而撞键失败的 INSERT 会在 PRIMARY supremum 上留下间隙锁，两个重放的下一次 INSERT 在同一间隙上互等成死锁——批量写入按幂等键上锁（锁在事务外），见 `MallCouponService.grant`。
- **排行榜口径只认 activity 域的 `ActivityRankingQueryService`（V25+V26 起）**：新增榜单或改口径时，把条件写在该服务里，**不要在 honor 域自己拼 where**——honor 只排序、定名次、存快照。积分榜排的是**累计获得**（非消费来源之和）而非余额，与积分中心 `totalEarned` 共用 `PointSourceType.CONSUMPTION_TYPES`；新增「消费类」来源时只改那一个集合，两边同时生效，否则同一个人在积分中心与排行榜会看到两个数。**往期名次一旦冻结就不该再变**：需要重排必须走 `POST /a/honor/rankings/snapshots?force=true` 的显式补跑（独立权限点），不要在读路径上做「顺手重算」。
- **积分只认账本（V24 起）**：读积分一律走 `PointService`（`balanceOf`/`batchBalance`/`summary`），**不要 `SUM(activity_attendance.points_award)`**——那只是单场活动的发放快照，手工调整/修正/兑换都不写它。写积分一律经 `PointService.record` 并**在调用方事务内**调用（积分与业务变更同成同败）；新增积分来源必须在 `PointSourceType` 分配**新的**类型码并明确它是否算「消费」（`isConsumption`，影响积分中心「已使用积分」口径）——复用旧码时 `uk_source` 会撞键，载荷复核只能发现**载荷不同**的那些，两笔恰好同人同额时仍会被当成重放**丢分**，故独占来源码是必要条件而非「反正有复核兜底」。
- **`@TransactionalEventListener(AFTER_COMMIT)` 里要写库，用 `PROPAGATION_REQUIRES_NEW`**（商城快递批的 `MallOrderService.onPaid`）：回调运行时外层事务已提交、资源仍绑在线程上，默认 REQUIRED 会加入那个已提交的事务——写进去的东西要靠连接归还时 autocommit 复位的隐式提交才落库，碰巧成立不等于正确。⚠️ **但这样一个线程同时占两条连接**（外层那条还没还，REQUIRES_NEW 又要一条）——挂在**高并发入口**（付款回调）上时，并发数一到连接池大小整池卡死（捐款批压测撞出）。高并发的发布方改为**在事务之外发布**、订阅方加 `fallbackExecution = true`（见 trade 行）；两个证书监听器挂在后台人工操作上，仍是原写法。**这类缺陷别靠并发去撞**：把连接池限成 1 条（`spring.datasource.hikari.maximum-pool-size=1` + 短 `connection-timeout`），单线程就能确定性复现，见 `PaymentListenerConnectionTest`。

- **变异验证：每次要重装「本轮动过的所有模块」，不只是这一条改的那个（2026-09-18 撞出）**：爱心企业批商品段的变异跨 donate 与 enterprise 两个模块，脚本每条只 `install` 被改的那一个，于是上一条变异的 jar 一直留在本地仓库里——后面几条变异的「必红」其实是上一条的效果（失败信息与上一条一字不差，正是那个信号）。跨模块的变异集，`runmut` 要么整反应堆 `install`，要么把本轮涉及的模块逐个重装。与下面那条 clean 构建是同一类错误的两种形态。
- **变异验证必须 clean 构建（2026-09-17 撞出）**：变异脚本用 rsync 把源码还原回去时保留的是原来**更旧**的修改时间，而上一条变异编出来的 class 更新——`install` 的增量编译认为无需重编，**上一条变异就悄悄留在了下一条的 jar 里**。那一轮里好几条变异「必红」其实是被上一条的残留弄红的（活动补全批的「资格档案改回快照读」clean 复验时**存活**，补了代报名用例才红）。变异脚本里的构建一律 `clean install`；判读结果时，报错若与上一条变异一字不差，先怀疑残留。
- **新增处置能力域要同时改三处（2026-09-18 私信批撞出）**：`SanctionScope` 的常量、`implying`（蕴含关系，承重条款 1）、`labelOf`，**外加 `assertKnown` 的取值上界**——那条守卫写的是 `scope > COMMUNITY_LIKE`，加了第 7 档却没改上界时，`implying` / `labelOf` 看着都齐全，禁言开单却在落库前被守卫拒掉（报「未知的处置能力域：7」），而闸门那一侧毫无征兆。社区禁言还要把新域加进 `SocialGovCodes.BAN_SCOPES` 才开得出来。
- **别对一个可能还不存在的人的行做范围 UPDATE / 当前读（2026-09-17 考试批又撞一次）**：`WHERE volunteer_id = ?` 在二级索引上命中零行时留下的是**间隙锁**，两个 id 相邻的人各持同一段间隙、再各自 INSERT 取插入意向锁，互等成死锁——与结对批登记同形。先普通读找出要改的行、再按主键改（前提是这个人的写入已被别的锁串行）。**按人的 Redisson 锁帮不上忙**：冲突发生在不同的人之间。
- **赛跑类并发用例要断言「每种结局都真的出现过」**：不偏置起跑时一方几乎总是赢（加锁读先到的那方），另一条分支一次都没跑到，用例照样全绿——`TradeBizEntryTest` 第一版就是 30:0。偏置三分之一先 A、三分之一先 B、三分之一同时，再 `assertTrue(aWins > 0 && bWins > 0)`。
- **第三方 webhook 的应答不要返回 `String`（2026-09-17 撞出）**：`String` / `ResponseEntity<String>` 配 `application/json` 会被前置的 Jackson 转换器再序列化成一个 JSON 字符串（外面包一层引号、里面全转义），对方按报文判定成败时（快递100）会把每一次都当失败重推。**直接写 `HttpServletResponse`**（见 `TradeCallbackController.write` / `LogisticsCallbackController`），HTTP 用例要断言报文是 JSON 对象（以 `{` 开头），只断言「包含某个词」在引号包着时照样绿。
