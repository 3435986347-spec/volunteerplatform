# 通知与处置

> 通知短信的统一入口，以及处置能力域的扩展方式（两者都在 auth，被各业务模块调用）。业务口径见 [`领域/11-后台管理系统.md`](../领域/11-后台管理系统.md)、[`领域/08-荣誉展示.md`](../领域/08-荣誉展示.md)。
> 2026-10-17 从《约定与踩坑》按主题拆出；一条一节，先说规则、再说为什么 / 撞过什么。

## 通知短信只走 `SmsNotifyService`

**通知短信只走 auth 的 `SmsNotifyService`**：新增通知场景时，先在 common 的 `SmsNotifyTemplate` 里登记（模板键 + 变量名 + **顺序**，并在 javadoc 写清落点），再在业务侧 `TPL.params(...)` 按序传值——**不要在业务代码里手拼 `Map` 或直接调 `SmsService.send`**：前者会把「变量名拼错」这类无征兆缺陷放回来，后者绕过了「等事务提交、异步派发、失败不影响业务」三条纪律。模板 ID 配在 `hengde.sms.templates.<键>`，生产走 `部署/api.env.example` 里的 `SMS_TPL_*` 环境变量（⚠️ 那是 systemd 的 `EnvironmentFile`，**值后面不能跟行尾注释**）。配了模板却没人调用是无害的；反过来，接了业务却漏配模板，启动时会 warn 列出来。

接一条新模板要改四处：业务调用、`SmsNotifyService.WIRED`、api yaml 的 `hengde.sms.templates`、`部署/api.env.example`；并在 auth 的 `NotifyTopic` 里把它归到一个话题（`NotifyPreferenceTest` 用反射钉住，没归类就红）。

## 新增处置能力域要同时改四处

**新增处置能力域要同时改三处（2026-09-18 私信批撞出）**：`SanctionScope` 的常量、`implying`（蕴含关系，承重条款 1）、`labelOf`，**外加 `assertKnown` 的取值上界**——那条守卫写的是 `scope > COMMUNITY_LIKE`，加了第 7 档却没改上界时，`implying` / `labelOf` 看着都齐全，禁言开单却在落库前被守卫拒掉（报「未知的处置能力域：7」），而闸门那一侧毫无征兆。社区禁言还要把新域加进 `SocialGovCodes.BAN_SCOPES` 才开得出来。
