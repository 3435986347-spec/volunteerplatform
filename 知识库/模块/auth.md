# auth 模块 · 认证、账号状态与跨模块的志愿者查询

> 代码：`代码/hengde-volunteer-auth/`。本页由根 `CLAUDE.md` 的「已完成」表下沉而来（2026-10-17）；
> 上半部分是**现行要点**，下半部分是按批次的原始记录（为什么这样做、撞过什么）。两者冲突时以上半部分与代码为准，并顺手修正下半部分。

## 职责

志愿者 / 后台 / 企业三套登录态，实名核验，志愿者 PII 加解密与只读查询（`VolunteerQueryService`），处置表与闸门（`volunteer_sanction`），通知短信统一入口，注销冷静期。

## 现行要点

- 三套 StpLogic：志愿者 `StpUtil`、后台 `StpAdminUtil`、企业 `StpEnterpriseUtil`，token 互不通用。
- 「登录成功」≠「账号可用」：禁用账号能登录，但只能看奖惩、提申诉（`BannedAccountGate`）；**禁用态绝不能 logout**，注销那一支才登出。
- 手机号、身份证 AES-GCM 密文 + HMAC 哈希；日志不打明文。任何新的「按手机号找人 / 查重」先调 `VolunteerDeactivationService.releasePhoneIfDue`。
- 处置「是否生效」按时间现算；闸门要父行锁 + 当前读两样；能力域的蕴含关系只在 `SanctionScope.implying`；加能力域要同时改 `assertKnown` 的上界。
- 通知短信：事务提交后才发、失败不影响业务、`SmsDispatcher` 必须是独立 bean；收件人口径只在 `listNotifiablePhones`（已注销不发、禁用照发）。
- 注销（协会答复五 乙-4）：申请即登出；7 天冷静期内任何一种登录都撤销注销（`LoginVO.deactivationCancelled`）；到期在请求闸门、登录、按手机号查找时当场落定。
- 实名核验返回码分流：服务侧故障 / 额度用尽抛「服务暂不可用」，不能当成核验失败。

**V32（第 5 批）新增处置措施 `volunteer_sanction`**（`SanctionService` 写 / `SanctionQueryService` 只读闸门）：能力域 1限制参加活动 / 2限制发布社区 / 3拒绝使用本程序，可带期限。**为什么落在 auth 而不是 honor**：处置是账号能力状态（与 `volunteer.status` 同性质），而闸门必须挂在 activity / publicity 的业务入口上——放 honor 会让那两个模块反向依赖 honor 而**成环**；auth 是三者都已依赖的模块。**「是否生效」永远按时间现算**（`status=1 AND effective_time<=NOW() AND (expire_time IS NULL OR expire_time>NOW())`），不靠定时任务改状态位——漏跑一次处罚就会超期继续生效，而「到期即恢复」是对志愿者的承诺。`SanctionScope.ALL` **蕴含所有能力域**，否则「拒绝使用」反而比「限制参加活动」管得少；报错必须带解除时间，且取「管得最久」那条时**要把 `expire_time IS NULL` 排在最前**——NULL 是不设期限即最重，而 MySQL 的 `ORDER BY ... DESC` 把 NULL 排在最后，直接 `orderByDesc` 会把永久处置报成「至 X 自动解除」，正好说反。

**订阅通知偏好（V4 个人中心补全批，V66 `volunteer_notify_pref`）**：`NotifyTopic` 把**每条短信模板恰好归到一个话题**（`NotifyPreferenceTest` 用反射钉住——新加模板不归类就红，没归类的一律按不可关闭处理），**奖惩与违规、活动取消、其他（未开发功能的模板）不可关闭**；`NotifyPreferenceService` 只存和默认（全开）不同的行（`INSERT … ON DUPLICATE KEY UPDATE`），`optedOut` 对不可关闭的话题恒返回空集（库里存了关闭也不生效）；**过滤只在 `SmsNotifyService.notifyVolunteers` 取号码前做一次**，业务调用方不判断。只管短信，站内提示照常留存。另有只读的 `AdminQueryService`（V4 投诉建议批：后台账号的部门、启用部门列表、姓名）。**通知类短信统一入口 `SmsNotifyService`（+ `SmsDispatcher`）**：业务侧只写一行「通知谁、用哪条模板、填什么值」，号码解密、模板解析、事务时机、异步派发、失败处理五件事收在这里。**放 auth** 是因为手机号是密文、解密要 `CryptoUtil`，而 activity/organization/honor 本来就都依赖 auth，不产生新方向也不成环。**三条不可动摇的口径**：① **必须等事务提交后才发**（`TransactionSynchronizationManager` 的 `afterCommit`）——短信撤不回而业务还会回滚，在事务内直接发会让志愿者手里躺着一条「您的报名已通过审核」而库里什么都没变；这与站内提示**刻意同事务**不矛盾：站内记录能跟着回滚一起消失，判据是**能不能撤回**。② **通知失败绝不影响业务**（模板没配/没手机号/火山拒收一律记日志返回），代价是参数写错在线上只留一行 ERROR，所以**用例必须真的断言短信内容**，只断言「审核成功」看不出来。③ **`SmsDispatcher` 必须是独立 bean**——`@Async` 与 `@Transactional` 一样靠代理，自调用静默失效（`CertificateAutoCreateListener` 记过同一课）；领域模块测试上下文没有 `@EnableAsync`，那里它同步执行、正好可断言。逐号发不拼多号码：拼一串时一个非法号会让整批被拒且分不清是谁。**收件人口径收在 `VolunteerQueryService.listNotifiablePhones`**（属账号状态语义，归 auth 一处说了算，不让 activity/honor 各自判断——散开就会有人漏掉且没有征兆）：**已注销不发**（注销＝要求停止打扰）、**禁用照发**（协会给禁用账号开的「只能看奖惩、提申诉」小口子，起点正是那条通知，挡掉等于把口子关上）；⚠️ 注销那条**已由协会 2026-09-16 确认**（注销＝退出协会，之后发什么都是打扰；见《协会待确认清单》回执四），不再是推论。
