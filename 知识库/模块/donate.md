# donate 模块 · 积分商城、捐赠与物资流转

> 代码：`代码/hengde-volunteer-donate/`。本页由根 `CLAUDE.md` 的「已完成」表下沉而来（2026-10-17）；
> 上半部分是**现行要点**，下半部分是按批次的原始记录（为什么这样做、撞过什么）。两者冲突时以上半部分与代码为准，并顺手修正下半部分。

## 职责

积分商城（商品 / 规格 / 兑换单 / 卷 / 核销员 / 快递 / 自提点）、公益捐书与物资流转、微心愿、结对、众筹、在线捐款与发票、物流查询与推送、捐赠统计、捐赠证书的事实来源。

## 现行要点

- 兑换：下单即扣分、占库存、占卷；**默认不审核**（`hengde.donate.mall.order-review=false`）——纯积分的单下单即成功、有现金的付款即成功，成功的单只能协会取消。
- 领取方式按商品设置（V95）；「老商品」的判定只在 `MallGoodsService.deliveryConfigured`；虚拟商品的兑换二维码只在本人兑换详情里给，商品页不下发。
- 库存 CAS 折成一条 `UPDATE … JOIN`；**CAS 失败之后的复核读必须是当前读**。
- 物资流转：运单 / 物资 / 箱 / 轨迹都带 `biz_type + biz_id`；碰箱子的动作一律先箱后物。
- 微心愿：受助人姓名学校密文，只有当前认领人看全文；看详情要已验手机号，并记录查看人与手机号。
- 结对：认捐额 ≠ 到账额；上限写在累加语句里；不对不存在的行加锁（直接插，撞键再当前读赢家）。受助人信息密文，只有已成立结对的人看全文。
- 众筹每个项目只收一种（捐款或捐物）。
- 捐赠证书：来源键在 `DonateCertRefs`，够格口径在 `DonateCertificateQueryService`，经事件交给 honor。
- 捐款：两本账（认捐 / 到账）；退款先改账、提交后再原路退；发票文件放私有存储。

**批量导入全成或全不成**，失败逐行报行号与原因（导入一半最难收拾）；上报单位按**名称**对上受赠单位主数据，对不上报错而不是静默置空。**来源名统一走 `DonateSourceTitleService`**：运单 / 物资的 `biz_id` 在不同 `biz_type` 下指向不同的表，只拿它去活动表查名字会把认领 id 当活动 id、**撞上同号活动就显示成别人的活动名且毫无报错**。排行榜第四板块同批放行（见 honor 行）。1 个权限点 `donate:wish`（共 61）。⚠️ **并发用例撞出来的两条，都是「CAS 失败之后的复核读必须是当前读」的同一形状**：① `claim` 的资格校验（两次普通读）原本在事务内，把 RR 读视图定死在赢家提交之前，CAS 输家复核时读到「还没人认领」，于是把「刚被别人认领」报成「这个心愿已经实现了」——改为资格校验在事务外、事务里第一条语句就是那条 CAS（`TransactionTemplate` + `doClaim`）；② `addItem` 为了判断「是不是微心愿的包裹」先做了一次普通读，同样让读视图提前定型，后面读运单头时会看到「已到货」而实际已被并发核对成「已核对」——新物资就以「待核对」落进一个没人会再核的包裹，改成 `selectHeadForUpdate` 当前读，并把「先锁认领、再碰运单」定为与实现心愿一致的加锁顺序（反过来会互等成死锁）。测试：`WishServiceTest`（全流程 + 每条拒绝条件 + 导入全成或全不成 + 密文落库）、`WishConcurrencyTest`（8 人抢认领 / 取消对寄出 15 轮 / 实现对取消包裹 10 轮 / 补录物资的 RR 隔离用例，**必跑**）、`WishStressTest`（`@Tag("stress")`，随机认领 / 取消 / 寄出搅拌后查四条不变量）、api 的 `WishApiFlowTest`（HTTP 全流程，**必跑**）。两处变异均已验证必红：`addItem` 的运单头读改回快照读 → 补录的物资落成「待核对」（期望合格实得待核对）；`DonateSourceTitleService` 不认微心愿 → 运单的来源名变回 null（正是改之前的行为）。

**结对批（V52 / V53 / V54，2026-09-16）**：Row 10（助学助困结对 + 受助方来信 + 捐赠证书）与 Row 16（项目众筹的项目管理与进度）。四张表 `donate_pair_project` / `donate_pair_record` / `donate_pair_letter` / `donate_crowdfund`。**全程不碰支付**（捐款接 trade 在捐款批），因此金额列叫 **`pledged_amount`（认捐额）而不是 raised**——叫 raised 会让前端把一个没到账的数当成「已筹到的钱」展示给捐赠人，那是会被追责的失真；众筹的 `raised_amount`（到账额）建了列但恒为 0。**认捐额只在「确认结对成立」时累加**，取消已成立的结对则退回；**上限条件写在累加语句里**（`pledged_amount + ? <= target_amount`）——登记时校验的是「当时的缺口」，两个人各自登记了不超过缺口的金额、两笔都确认就会越过受助金额，登记那一刻的校验挡不住（并发用例撞出来的）。**参加人数不存列**、按有效登记现算（存列就有两个口径，本项目为此栽过三次）。「一人一项目至多一条有效登记」靠生成列唯一键 `uk_active_pair`，取消后释放可重登记；登记 / 撤回 / 确认 / 取消四个动作都以「当前读锁住那条活登记」开头。

**本批不建受助人 PII 列**：Row 10 只要求展示项目图片、金额与进度，没有要求展示受助人姓名 / 学校（微心愿建密文列是因为 Row 12 明确要展示并打 `*`，这里没有那条需求）。**受助方来信分公开信与私信**：写给某一位结对人的信只有他看得到，过滤在服务端——那种信里往往有受助方的具体情况；**私信只能写给已成立的结对**（2026-09-27 补：此前待确认 / 已取消的登记也收得到，而志愿者端按「本人的登记」过滤，他就看得到）。1 个权限点 `donate:project`（共 62）。**捐赠证书（Row 10「捐赠后需要自动生成证书」）**：`CertificateType.DONATION = 3`，触发点取《协会待确认清单-v3》⑨ 的默认「**结对成立即出证**」。⚠️ **幂等键必须另起**：`uk_slot_cert`
