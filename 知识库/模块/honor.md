# honor 模块 · 荣誉：排行、勋章、证书、奖惩

> 代码：`代码/hengde-volunteer-honor/`。本页由根 `CLAUDE.md` 的「已完成」表下沉而来（2026-10-17）；
> 上半部分是**现行要点**，下半部分是按批次的原始记录（为什么这样做、撞过什么）。两者冲突时以上半部分与代码为准，并顺手修正下半部分。

## 职责

排行榜（往期冻结快照）、勋章与榜样、电子证书（活动 / 捐赠）与证书样本、奖惩中心（两级审核、申诉、处置）。

## 现行要点

- 排行：当期实时聚合、往期读冻结快照；「是否已冻结」只看完成标记表；三个榜的口径在 activity。
- 勋章：样式审核与发放审核是两条线；改已启用的样式退回重审；发放侧用当前读取勋章。
- 证书：活动证书在秘书确认考勤后自动建、PDF 懒渲染；**公章在样本上，缺样本拒绝出证**；下载只发短期签名 URL，计数语句是最后一道闸。
- 证书字体：思源宋体（SIL OFL 1.1，字体与许可证在 `fonts/`）**子集嵌入**每张 PDF，称呼四号、正文与编号小四、字距多四分之一个字，编号逐位等距；主标题在协会样本上，不由系统画。重新生成走 `POST /a/honor/certificates/{id}/re-render`：先传新对象再按旧 key 换，旧文件保留，只认系统渲染件。
- 捐赠证书（协会答复五）：结对成功 / 心愿实现 / 捐物核对合格 / 众筹捐款到账时由 donate 事件触发，只用 `donation` 样本；够格口径与正文在 donate 的 `DonateCertificateQueryService`。
- 奖惩：组织部初审 → 理事会终审；奖励不经初审；持终审权开单即通过（判据是开单人的权限，不是请求字段）；五件效力全挂在终审那一刻；申诉截止落库；只有处罚可申诉。
- 三档处置按部门拆权限点（V85），互不蕴含；提前解除与开出同一档要同一个点。

## 按批次的记录

**证书中文乱码与字体（2026-10-30，前端反馈 + 本机复现）**：`CertificatePdfRenderer` 一直是 STSong-Light + Identity-H 且不嵌入，文件声明 `Adobe-Identity-0`，阅读器无从把编码对到汉字，套印内容全是乱码（接口 200、文件非空，所以一路没人发现）；类注释写的 UniGB-UCS2-H 与实现不符。
只换 UniGB-UTF16-H 不够：靠阅读器替代字体，数字字宽对不上、挤在一起，基本多文种平面以外的字（`𠮷`、emoji）在关闭文档时抛空指针、接口 500。所以改成嵌入思源宋体（jar 大 11.6 MB，单张证书约 170 KB），字体在启动时解析，缺文件或文件坏了应用起不来。honor 的 POM 去掉了 font-asian 的声明（`itext-core` 本身也带它，部署包里还在，只是不再用）。macOS 自带的宋体许可标记禁止嵌入，不能拿来用。
撞到的三件事：① 这款字体的数字是比例宽度，`1` 窄一成多，编号要逐位配字距补到同一步长（`certNoLine`）；② 字库里没有的字（`𠮷`、emoji）显示成方框，不失败；③ 「力」「月」「长」「巳」等与同形部首码位共用字形，iText 写 ToUnicode 时记的是部首码位：显示无误，但从 PDF 复制、搜索得到的是部首，用例比对时要先归一（`assertReads`）。
字号字距是需方看样定的。已渲染的文件不会自动换，重新生成见现行要点；不做迁移批量清 `file_key`——样本若已删，能看的证书会变成打不开。用例 `CertificatePdfRenderTest`，`CertificateServiceTest` 的 `reRender_*`。

`PointSourceType.CONSUMPTION_TYPES` 一份定义）。**并列名次按 volunteerId 升序、名次仍连续**（定序必须确定，否则快照重跑名次会变，冻结就没意义）。`RankingPeriod`（support 包）是 **periodKey ↔ 调度中心+自己的库表，硬接会得到跑不起来也无法验证的半成品），将来换 XXL-Job 只是在本类旁加一个 `@XxlJob` 处理器调同一个方法、业务代码不动。**冷静期** `hengde.honor.ranking.freeze-delay-days` 默认 7 天：时长要等秘书部确认、积分要等发放，周期一结束就冻会把没结算完的数据定死；冷静期**只约束定时任务**，后台显式补跑不受限。定时任务**每天跑**而非「每月 1 日跑」——按月触发一旦当天服务不在线，那个月的快照就永久缺失，每天跑配合幂等可自愈。`rank_type=4` 微心愿**自 V3 微心愿批起放行**（数据源是 donate 的 **V2 第 3 批·勋章与榜样（V28）**：**双重审核**——①样式：`MedalService` 录入落草稿 →`submit` →`approve`/`reject`（CAS），**只有 `MedalStatus.ENABLED` 的勋章可发放**；**改已启用/已停用的定义会退回待审核**（否则可先提交素净图标过审、通过后再改成别的，样式审核形同虚设），纯展示的 `sort` 走独立入口不触发重审；停用不影响已生效的发放（志愿者拿到的勋章不该因协会下架样式而消失）；有阈值的条件必须给阈值、手动授予强制清空阈值（**`update` 用 `LambdaUpdateWrapper` 显式 `.set()` 而非 `updateById`**——MP 默认跳过 null，否则「清旧阈值」「清上次审核痕迹」都会静默失效，这条是被测试当场抓到的）。②发放：`MedalGrantService.apply` 落待审、**志愿者端不可见**；`approve` 顺序钉死「校验勋章仍 ENABLED → CAS 置生效 → 再入账」（先发分再 CAS，CAS 失败时第一次的分已白发）；附带积分用 `PointSourceType.MEDAL(3)`（V24 预留的来源码，`source_id`=发放记录 id，`uk_source` 保幂等），**金额取发起时快照而非审核时现读**（申请与审核之间定义被改，审核人批准的就不是他看到的数）。**防重复授予靠 DB 生成列唯一键 `uk_active_grant`**（待审/已生效时取 `medal-volunteer`，驳回后为 NULL，仿 V9 `uk_active_volunteer`）——放数据库而非「先查再插」是因为后者并发下必漏；**驳回不占键故可重新发起**，用死约束会把人永久挡在门外。`myMedals` 只统计已生效的发放，并给出**获取进度**——进度不依赖自动发放引擎（**自动判定本批未做**，`grant_type=2` 仅占位），三种阈值的当前值直接读既有服务：时长/次数取 `ServiceRecordService.batchStatsByVolunteerIds`、积分取 `PointService.summary().totalEarned` 即**累计获得**（与排行榜/积分中心同口径，花掉积分不该丢进度），百分比封顶 100。`RoleModelService` 榜样与 publicity 轮播图同构（新增落下架、上下架独立、志愿者端只看已上架），**不走审核**——审核是勋章那条线的要求，上下架本身就是发布闸门。图标上传走 `POST /a/files/upload?dir=medal`（`FileUploadController` 新增该 dir 分支，权限 `honor:medal`，仅收图片）。控制器 `AdminMedalController` `/a/honor/medals`+`/medal-grants`、`AdminRoleModelController` `/a/honor/role-models`、`MedalController` `/v/honor/medals`+`/role-models`（仅需登录，志愿者 id 取登录态不接受入参）。

**评审后补正（同批内，4 条 P1 + 3 条 P2）——核心是「先查一下、再据此动作」，而查与动作之间隔着别人的一次提交**：① `update` 拒绝改「待审核」的勋章，且该限制写进 UPDATE 的 WHERE（`ne(status, PENDING)` + 影响行数判定）——只在方法开头 if 拦不住「修改先完成、审核后完成」，因为那个 if 读的是 RR 快照；② `updateSort` 改为只发 `SET sort` 一条语句，**不再读实体再 `updateById` 写回**（否则并发的「改已启用→退回重审」会被整行覆盖回已启用，等于绕过样式审核）；③ 发放侧 `apply`/`approve` 取勋章改**当前读共享锁** `HonorMedalMapper.selectByIdForShare`——`@Transactional` 里第一条 SELECT 就把读视图定死了，普通查询读不到别人后来提交的停用，一枚已撤下的勋章照样生效发分；`delete` 相应取排他锁并入事务，杜绝「删完再插」的孤儿发放记录（V28 无外键）；④ 两个**读列表**放宽为 `SaMode.OR`「管理权或对应审核权」——只有审核权却读不到列表只能盲审；⑤ `myMedals` 改为「已启用 ∪ 本人已生效发放所引用的」，否则样式一停用志愿者手上的勋章就消失，与「停用不影响已生效发放」的承诺相反；⑥ **进度口径改走 `ActivityRankingQueryService.totalServiceMinutes`/`totalAttendanceCount`**，不再用 `ServiceRecordService.batchStatsByVolunteerIds`——后者是志愿者管理列表的粗口径，不筛活动状态也不要求有签到，草稿/已取消活动上的脏考勤会把进度顶上去，与排行榜/看板各显示一个数；⑦ 权限点注释收窄措辞：权限拆分只让「分开授权成为可能」，**并不禁止同一账号兼有两点或超管自审**，要强制双人复核得另加创建人字段校验（本批未做）。测试 `MedalServiceTest` 17 + `MedalGrantServiceTest` 27 + `MedalReviewIsolationTest` 6 + `RoleModelServiceTest` 9（honor 全量 84）。**新增的 `MedalReviewIsolationTest` 是这类缺陷的通用打法**：顺序调用的用例（先停用、再审核）根本没有窗口、永远绿，必须在显式 `ISOLATION_REPEATABLE_READ` 事务里「先读建快照 → 另一连接改并提交 → 断言快照仍读到旧值（用例有效性自检）→ 再调被测方法」，不靠 sleep 撞运气。七处关键行为均做过变异验证，全部必红：去掉发放前的样式校验 / 改已启用不退回重审 / 发起即生效 / 进度改用余额 / `updateSort` 改回 `updateById`（status 由 1 变回 2）/ 去掉 `ne(status,PENDING)` / 两处当前读改回快照读 / 进度改回粗口径（脏时长 900、脏次数 1）。依赖 common/auth/activity（无环；经 activity 传递引入 redisson starter 故测试需 Redis）；api pom 已加 honor 依赖，`@EnableScheduling` 在 api 的 `AsyncConfig`。

**V2 第 4 批·电子证书核心（V31）**：需求 xlsx Row 36「参加完活动后**自动生成一个盖章的电子证书**……电子证书预览和下载」+ F 列「批量上传pdf证书 / 删除指定某人证书 / 设置某个活动的电子样本」。**落地方式＝权益自动创建 + PDF 懒渲染**：`ServiceRecordService.secretaryConfirm` 与 `ActivityBackfillService.applyBackfill` 各发一条 `AttendanceConfirmedEvent`，`CertificateAutoCreateListener`（**独立组件**，不能与 `createForSlot` 同类——自调用会让 `@Transactional` 静默失效）以 `AFTER_COMMIT` 建证书行；PDF 到首次预览/下载才渲染。**幂等键 `uk_slot_cert(type, volunteer_id, slot_id)`**（协会 2026-07-30「一场活动一个证书」，V30 补上 `slot_id` 后才可落地）；并发下输的一方捕获 `DuplicateKeyException` 读赢家那行，**不是靠先查挡住、是靠唯一键挡住**。**发证资格闸门在 `createForSlot` 内**（要求活动域有「秘书部已确认」的考勤，走窄接口 `ActivityCertificateQueryService`）——放在这里而不是某个入口，是因为批量上传按文件名手机号匹配，一个错号就会给从没参加过的人发证且那人能下载。**渲染把协会「电子样本」PDF 当底图套印**（`FileStorageService.download` 为此新增）——**公章在样本上**，这是「盖章」这条硬要求的落点；样本缺失或读不出一律**拒绝出证**，绝不退回自绘无章版式（那比没有更糟）。样本作用域用显式键 `scope_key`（`activity:{id}` / `global`，先查活动专属再退全局），唯一键建在**只含未删行的生成列** `active_scope_key` 上——裸 `UNIQUE(scope_key)` 会让软删的样本继续占位，管理员删了就再也建不出同作用域的新样本，界面死锁。**懒渲染并发**：按 certId 上 Redisson 锁 + 锁内二次读 + `UPDATE ... WHERE file_key IS NULL` 的 CAS 回填；**系统渲染件与后台上传件分处不同对象前缀**（`certificate/system/` vs `certificate/upload/{certNo}-{rand}`）——共用一个 key 会让两者互相覆盖，协会原件可能被系统件顶掉且无痕迹。**下载**：只发短期签名 URL（默认 120s，受 `hengde.oss.presign-max-ttl-seconds` 二次约束），**签发前用 `incrementDownloadCount` 的影响行数作最后一道闸**（该语句自带 `is_deleted=0`）——渲染要几百毫秒，期间证书可能已被撤销，而签名 URL 一旦交出去就撤不回来；归属不符与不存在返回同一句话，防枚举。**软删**留痕删除人/时间/原因，软删行**仍占 `uk_slot_cert`**（重跑复活原件、保留原编号＝口径 b），后台列表须 `includeDeleted=true` 才找得回 id 去 restore。**`CertificateReconcileJob` 是唯一的自动最终一致性保证**：事件是进程内不持久的，而 `secretaryConfirm` 的 CAS 一次性（0→1）、失败后**永不再触发**，只在监听器里 catch+log 等于把一次失败变成一条无人读的日志；该任务定期扫「已确认考勤却无证书」补建（`createIfAbsent`，**刻意不复活软删行**——软删是管理员的明确意思表示）。**但它有回看窗口**（`reconcile-lookback-hours` 默认 72h）：**不设下界会让这个每小时跑的定时任务第一次运行就给所有历史活动批量发证**，而「改造前已结束的活动是否补发」协会尚未答复，等于让 cron 替协会答了待决问题、且证书发出去收不回。窗口本身又是个洞（事件丢失 + 停机超窗口 ⇒ 永久缺失且无人发现），故配 `POST /a/honor/certificates/reconcile?since=&activityId=` 作**人工救济**，**范围必须显式给出、两个都不给直接报错**；协会给出历史口径后用的也是它。**两条索引是这两条新查询的承重件**：`activity_attendance` 加 `idx_secretary_time(secretary_status, secretary_time)`（原表无任何以 `secretary_time` 打头的索引，时间谓词会降级成逐行过滤，代价随历史总量而非窗口增长）并删去被它包含的 `idx_secretary`；`honor_certificate` 加 `idx_slot(slot_id)`（差集查询 `type=? AND slot_id IN (…)` 只吃得到 `uk_slot_cert` 的 `type` 前缀）。**加时间/新维度过滤时先看现有索引的前导列**——V25 记过同一课。**样本的 `fileKey` 只收 `POST …/certificate-templates/file` 产出的 key**（前缀校验），理由与不收 `scopeKey` 相同：随手写的字符串要等到那个活动第一次出证才报「文件读取失败」，而那时是志愿者在点下载；样本修改走 `LambdaUpdateWrapper` 显式 `.set()` 并**查影响行数**（`updateById` 跳 null 会让 `layout` 再也清不掉，且并发软删时 0 行仍报「修改成功」——与 `MedalService` 那条是同一形状）。**撞唯一键之后的两条**（都是「先查一下再据此动作」的老形状，与勋章/积分那批同源）：① 取回赢家必须用 **`FOR SHARE` 当前读** `selectBySlotForShare`——RR 下快照在事务第一次 SELECT 就定死，普通读看不见赢家后来提交的行，会把 `uk_slot_cert` 冲突误判成 `uk_cert_no` 冲突（换号重试到耗尽、日志指向编号生成、最后误报「没补完」）；**不用 `FOR UPDATE`**，因为报重复键时 InnoDB 已给冲突行加了 S 锁，多个 loser 再抢 X 会互等成死锁（`PointRecordLockOrderTest` 已钉死这一课）。② 确认撞的是 `uk_cert_no` 时**换号重试**（上限 5）——编号是「秒 + 6 位随机」，同秒只有 10^6 个取值，批量补发把上千张挤进同一秒时碰撞是常态，而批量路径逐条 catch，原样抛出就变成「那个人静默无证、接口却报补完了」。⚠️ 批量上传路径全是自调用、事务注解不生效，autocommit 下**照不出** ① 这类缺陷，别拿它当覆盖。**跨域一律走窄接口**：`ActivityCertificateQueryService`（活动/场次/考勤）与 `VolunteerQueryService.findIdsByPhones`（手机号换 id，honor 不接触 PII 密文），不直连对方 Mapper。

**V2 第 5 批·奖惩中心（V32 + V33）**：需求 xlsx Row 41「各类违规记录和奖励均需**组织部同学审核才可显示**，审核之后…有 **7天申诉期**」+ 原型 P109。`honor_reward_punish` 一张表统管奖与惩；**三条效力全部挂在「审核通过」那一刻**——对志愿者可见、积分入账（`source_type=6`，第 1 批预留的码）、处置生效，待审核期间只是草稿，免掉「先罚后审、审不过再冲正三处状态」。

**V40 起「审核通过」＝两级里的终审**（协会 2026-09-02 答复问题二）：`review_status` 加一档 3「已初审待终审」，`approve` 拆成 `firstApprove`（组织部，**不产生任何效力**，只把单子往前推一格）与 `finalApprove`（理事会，五件效力一次落地）；**奖与惩不对称**——处罚从下往上要经组织部初审，**奖励开单即落待终审、不经组织部**（「各部门都可以提出奖励申请，理事会审核」）；开单人持 `honor:reward-punish-final` 时走「开即通过」快捷通道（「理事会的同学开单的则自动完成」「紧急情况下由理事会的同学直接进行处罚的，则自动审核完成」），与终审共用 `applyApproval` 一段代码——两条路的结果必须逐字相同，分成两份实现迟早漂开一件。⚠️ **快捷通道的判据是开单人的权限，不是请求体里的开关**（判定在控制器，与 `assertScopeAllowed` 同一形状）——做成开关的话任何有开单权的人都能给自己开免审通道；`RewardPunishTwoStageTest` 有一条反射用例专门盯着 DTO 不许长出这种字段。⚠️ **终审的 CAS 条件必须是 `eq(REVIEW_FIRST_PASSED)` 而不是 `ne(REVIEW_APPROVED)`**，后者会让没初审的处罚被一步批掉、绕过组织部。初审痕迹落 `first_review_by`/`first_review_time`，`reviewed_by`/`review_time` **此后专指终审**；「是否走了快捷通道」不另存列——`type=处罚 且 first_review_by IS NULL 且已通过` 即是（奖励本就不经初审，不构成歧义）。⚠️ **但这条推导只对 V40 之后新建的行成立**：改造前一级审核通过的行，`reviewed_by` 是组织部的人而 `first_review_by` 为空，照上面读会被误判成走了快捷通道；迁移**刻意不回填**（复制一份会造出「同一个人既初审又终审」的假记录，比含义漂移更糟），实践中这批数据不存在（第 5 批从未合入 main）。驳回**两档都可以驳**（只让初审驳的话，单子到理事会手上就只剩「批」这一条路）。**申诉截止时刻在通过时落库定死**，不由 `review_time+7天` 现算（现算会让「把 7 改成 3」追溯性作废在途的申诉权）；**只有处罚可申诉**（P109 的申诉按钮只画在处罚上）。**申诉成立 = 撤销处置 + 反向流水**，且反向流水**不能复用 `source_id`**（`uk_source(6,id)` 已被原始那笔占住），走 `source_id=null + requestId=sys:rp-revert:{id}`——该前缀**系统保留**，`PointService` 对非奖惩来源拒绝使用。⚠️ **守卫不能只按字面比对，补上大小写也还不够**：`uk_request_id` 的「相等」由排序规则决定（默认 `utf8mb4_0900_ai_ci` 既忽略大小写、**又忽略重音**），Java 的相等由码点决定，两者的差集就是漏洞——`sýs:rp-revert:1` 过得了 Java 守卫却占住库里同一个键，那张单日后申诉成立时，反向流水撞上这条已存在的键，载荷复核发现来源码不同而抛「积分入账冲突」，**整个受理事务回滚**——处置没解除、分没退、申诉也办不成，直到有人手工清掉那条占位流水（不是「静默跳过、只解除处置不退分」的半提交）。

**V34 起该列固定为 `utf8mb4_0900_bin`**（让两种「相等」重合；⚠️ 这个排序规则要 **MySQL 8.0.17**，项目最低版本因此不是 8.0.16），**并把幂等键限死在 ASCII 安全字符集 `[A-Za-z0-9:._-]`**（`PointService.REQUEST_ID_PATTERN` + `PointAdjustDTO` 的 `@Pattern`）——不在 Java 里追着枚举排序规则的等价类，重音/全角/尾空格列不完。**处置表 `volunteer_sanction` 落在 auth 而不是 honor**——闸门要挂在报名/签到/社区发帖这些业务入口上，放 honor 会让 activity/publicity 反向依赖 honor 而成环。**到期靠比时间不靠 cron 改状态位**（漏跑一次处罚就超期继续生效）；`effective_time` 必须**向下取整到秒**，因为 MySQL `DATETIME` 写入是**四舍五入**，`.700` 会存成下一秒，处置在最多 0.5 秒里明明已施加却挡不住人（这条是测试先红三条才追出来的）。**闸门要两样东西，缺一不可**：① **串行化**——与处置写入共同锁住 `volunteer` 那一行（`impose` 取 X、闸门取 S）。报名持的 `lock:enroll:volunteer:` 只串行化报名之间，管不住奖惩审核那一侧；而要挡的那条处置在闸门查的时候**还不存在、锁不住不存在的行**，所以只能锁一行必定存在的稳定父行。`approve` 复核志愿者也因此一开始就取 X（先 S 后 X 是锁升级，两个并发审核会死锁）。② **可见性**——闸门的处置查询本身必须是**当前读**（`VolunteerSanctionMapper.selectBlockingForShare`）。⚠️ **只加父行锁是不够的，这一步曾漏掉**：父行锁只买到「对方提交不完我就等着」，买不到「等到之后能看见」——RR 的读视图在本事务**第一次一致性读**时就定死，而 `doProxyEnroll` 出于隐私顺序必须先跑同组校验（普通读），读视图那时已经建立，普通查询看不见这期间提交的处罚。回归用例 `EnrollmentGateIsolationTest`——它同时钉住反方向（`impose` 自己也取父行 X 锁）与真实入口（有一条直接调 `proxyEnroll`，而不是只比较两个查询方法）。⚠️ **代报名走批量版 `assertNoneRestricted`**：当前读在 RR 下连间隙一起锁，范围可能盖到本批后面的志愿者，逐个「锁父行→读处置」会与 `impose` 成环（ER_LOCK_DEADLOCK）；批量版**先按 id 升序把父行锁全部拿齐再读**。单人入口没有第二步，仍用 `assertNotRestricted`。**`assertNotRestricted` 不在事务里直接抛 `IllegalStateException`**：`FOR SHARE` 在 autocommit 下随语句释放，闸门看着还在、串行化边界已经没了，且毫无征兆。**审核复核志愿者用当前读**（`getGrantEligibilityForUpdate`）：快照读看不到开单之后别人提交的注销；且**「非 null 就放行」漏掉 `status=2`（已注销）**——行还在、账号已注销，照样能入账一笔无主积分。禁用（`status=1`）**奖励与处罚都照常审核**（协会 2026-08-11 第 5 条）。⚠️ **这条口径来回改过两次，两次的理由不互相反驳**：第 6 轮改成「一律不批」，因为当时 `SaTokenConfigure` 对 `status != NORMAL` 拦掉全部 `/v/**`（含奖惩列表与申诉入口），通过审核＝处罚立刻生效而 7 天申诉期在他够不到的地方流逝；协会选了另一条路——照常批，但**给禁用账号开个小口子、只能看奖惩和提申诉**，于是 `ensureLoginable` 现在给禁用账号发 token（**「登录成功」不再等于「账号可用」**），`BannedAccountGate.EXEMPT_PATHS` 放行 logout/奖惩记录/申诉/处置查看/站内提示五条。

**V2 联调补口（V43–V45，2026-09-06，应小程序侧《V2后端待办清单》）**——三件事，都是「后端做完了但小程序接不上」而不是功能缺失：① **榜样补 `model_type`/`summary`/`link_type`/`publish_time`（V43）**。`link_type` 是关键：此前只有一个 `link_url`，小程序拿到一串地址**无从判断该怎么打开**——内部路由要 `navigateTo`、备案网页开 WebView、外部链接在小程序里根本打不开只能复制；靠「是不是 https 开头」猜会把后两者混成一类，而它们行为完全不同。出参同时给码值与稳定英文名（`NONE`/`PAGE`/`WEB`/`EXTERNAL`），免得两端各维护一份映射。⚠️ **V44 单独把存量 `link_url` 归类**（`/` 开头→PAGE、`https://`→WEB、其余非空→EXTERNAL）——不归类的话那些本来点得开的榜样会在小程序上变成不可点（**静默的功能回退**），更糟的是运营下次编辑该行时表单按 `link_type=0` 提交，后端就把 `link_url` 一起清掉、**永久丢失**。ALTER 与 UPDATE 必须分两个文件：ALTER 隐式提交后 UPDATE 再失败，重跑会撞「列已存在」。`publish_time` **只在首次上架写一次**，下架不清、再上架不覆盖、改内容也不覆盖——否则临时下架改个错别字再上架，它就在小程序「最新」里跳到最前面。「不跳转却填了链接」**报错而不是静默清空**（静默清空最糟：填了地址、保存也提示成功、链接却没了）。② **三个 `/v` 列表改分页**（`/v/honor/role-models`、`/certificates`、`/reward-punishes`）：裸数组没有 total，小程序做不了触底加载。**这是破坏性改动**，已与小程序侧约定同步切换。③ **申诉凭证（V45）**：`appeal_images` 逗号分隔存最多 6 张，张数与逗号在 service 当场校验、**不靠列宽兜底**（非严格模式静默截断会让受理人看到半截 URL 而提交却是成功的）。⚠️ **上传单开一条 `POST /v/files/appeal-image`，不并进 `/profile-image` 的 dir 白名单**——它必须被 `DenyAllUseGate` 与 `BannedAccountGate` 放行，而那两条清单**按路径**写：挂在 `/profile-image` 上，要么被判「拒绝使用」和被禁用的人**申诉提得出去却举不了证**（申诉路径是残的，而他们最需要举证），要么为放行它把整个 `/profile-image` 开出去、顺带让被禁用账号能改头像。测试 honor 191（`RoleModelServiceTest` 9→18、`RewardPunishServiceTest` 36→40）；三处变异已验证：去掉 publish_time 的「仅首次」条件 / 「不跳转带链接」改回静默清空 / 去掉凭证 6 张上限，均必红。
