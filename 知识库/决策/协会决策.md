## 一、部门与授权

### XH01 · 现行部门：理事会 + 组织部 / 秘书部 / 宣传部；监察部、分队管理部已撤销
- **日期 / 原编号**：2026-08-11 奖惩第 4 条；2026-09-16 丙-3
- **协会原话**：「现在目前五个部门整合成三个了（秘书部、组织部、宣传部）」（8/11）；9/16 要点：监察部与分队管理部**一年前已撤销**。
- **现行口径**：部门只有理事会、组织部、秘书部、宣传部。**材料里凡写监察部、分队管理部的，一律按 XH02 / XH27 / XH28 改读。**
- **落点**：部门没有主数据表，是 `admin_user.department` 的一段文字（按部门授权、投诉路由都按这段文字逐字匹配，见 XH02、XH28）。
- **推翻**：原型 P19 的六部门下拉；需求表 Row 73「监察部拥有全部限制能力」（→ XH02 理事会）；Row 43「投诉默认到监察部」（→ XH28）；Row 60 分队审核归分队管理部的读法（→ XH27）。

### XH02 · 三档限制按部门：活动→组织部、社区→宣传部、拒绝使用→秘书部；账号恢复→理事会；理事会拥有全部限制权限
- **日期 / 原编号**：2026-09-16 丙-3（需方 2026-09-27 原话复述可互证）；8/11 奖惩第 5 条
- **协会原话（要点）**：限制参加活动 → 组织部 / 限制发布社区 → 宣传部 / 拒绝使用本程序 → 秘书部 / 账号恢复 → 理事会；理事会拥有全部限制权限。
- **现行口径**：三档各一个权限点、**互不蕴含**；开出与提前解除同一档要同一个点。
- **落点**：V85 `honor:sanction-activity`、`honor:sanction-community`，`honor:sanction-all` 收窄为「拒绝使用本程序」；V86 / V92 按 `TRIM(admin_user.department)` 一次性补授（理事会三档 + `user:restore`）；写错字、没填部门的账号由 `SanctionPermissionAudit` 启动时 WARN 列出，超管手工补。
- **推翻**：Row 73「监察部拥有全部限制能力」；V36 时 `honor:sanction-all` 写作「监察部」。

### XH03 · 「审核」＝该部门下的成员账号都能操作；上线时按部门授权
- **日期 / 原编号**：2026-09-16 丙-1；2026-10-16 丁-1（V3 ①）
- **协会原话（要点）**：理事会也算一个部门，会换届、会新增和取消；审核是指这个部门下面的成员账号都可以操作，其他部门同理。10/16：同意审核权限上线时按部门授。
- **现行口径**：系统仍是**按账号**授权（`admin_permission`，超管逐个勾）；「按部门授」是上线时的授权工作，不是结构改动。商城兑换审核（若打开审核开关）授给哪个部门同此。
- **落点**：没有「部门继承权限」的机制。⚠️ 换届、新增成员时要人工补授，**漏授没有任何征兆**——改成部门级继承是一次结构性改动，未做。

### XH04 · 理事会是组织架构里的一个节点
- **日期 / 原编号**：2026-08-11 追认（回执二问题 C，取 A）
- **协会原话**：「理事会在组织架构里面也有，是组织架构」。
- **现行口径**：架构节点＝部门，理事会应有一个节点。
- **落点**：V101 在协会根节点下补种「理事会」，排在组织部前面（原型 P19 的顺序）。V5 种子只种了协会 + 组织部 / 秘书部 / 宣传部，2026-10-17 核对时发现从没补种过；需方当天拍板「理事会节点也建出来」。树里任何位置已有未删的「理事会」（后台先建过，挂在根下、部门下或另起顶层都算，名称去首尾空格比较）时迁移不再插第二个（`V101CouncilNodeMigrationTest` 钉住）。理事会成员仍由超管在后台放进这个节点。

## 二、奖惩与处置

### XH05 · 处罚两级审核：组织部初审 → 理事会终审；持终审权的人开单即通过
- **日期 / 原编号**：2026-09-02 问题 2.1、2.3（细化 8/11 奖惩第 3 条）
- **协会原话（要点）**：理事会开单则自动完成；从下往上的，组织部审完再到理事会审；未终审前志愿者看不到；原则上两步，紧急情况理事会直接处罚则自动完成。
- **现行口径**：判据是**开单人有没有终审权**（`honor:reward-punish-final`），不是请求里的一个开关——否则任何能开单的人都能给自己开免审通道。**五件效力**（置状态、定申诉截止、积分入账、施加处置、站内提示 + 短信）全挂在终审那一刻。
- **落点**：V40 `review_status` 加 3「已初审待终审」，`RewardPunishService` 拆初审 / 终审；控制台把 3 单列为「待终审」。
- **推翻**：8/11 第 3 条「开单和审核可以一人完成，处罚或奖励直接生效」——现在只在开单人持终审权时成立。

### XH06 · 奖励：各部门都可提出，理事会审核，不经组织部；理事会发起的直接通过
- **日期 / 原编号**：2026-08-11 奖惩「奖」；2026-09-02 问题 2.2、6.3
- **协会原话**：「奖：各部门均可录入奖励，审核由理事会审核」（8/11）；9/2 要点：奖励都要理事会审核；理事会发起的直接通过。
- **落点**：V40；奖励开单即「待终审」。

### XH07 · 申诉一律由理事会受理（活动类、社区类都是）
- **日期 / 原编号**：2026-08-11 奖惩第 2 条；2026-09-02 问题 6.2；2026-09-16 丙-2
- **协会原话**：「申诉：用户申诉后由理事会审核」（8/11）；9/16 要点：申诉均归理事会审核。
- **现行口径**：只有处罚可申诉；申诉期 7 天，截止时间在**终审通过时落库定死**。
- **落点**：独立权限点 `honor:reward-punish-appeal`，授给理事会账号即可，代码不判部门。协会没要求「审核人不得受理自己批的单」，未做人员分离校验。

### XH08 · 开单与审核可以是同一个人
- **日期 / 原编号**：2026-08-11 奖惩第 3 条（回执二对 5️⃣ 附问的解读）
- **现行口径**：不做 `reviewBy != createBy` 校验；职责分离靠权限点拆分（开单、初审、终审、申诉各自独立）让它「成为可能」，不强制。

### XH09 · 处罚单被驳回或申诉成立后，同一条违规可以再开一张「轻一点」的单；轻重由理事会人工把关
- **日期 / 原编号**：2026-08-11 奖惩第 8 条（回答 9️⃣、9-附）；2026-09-02 问题 3.1 选 A
- **协会原话**：「处罚单被驳回或申诉成立后：用户申诉成立但觉得不惩罚不行，则可以给他开第二张轻一点的处罚单」。
- **现行口径**：驳回、申诉成立都释放「一条违规至多一张有效单」的占位；新单**不做轻重比较**。
- **落点**：V35（驳回释放）、V38（申诉成立释放）`uk_active_violation`。
- **推翻**：V35 时「申诉成立的单继续占位」的推论。

### XH10 · 禁用账号开一个小口子：只能看奖惩、提申诉；禁用期间照常开单审核
- **日期 / 原编号**：2026-08-11 奖惩第 5、7 条（回答 7️⃣）
- **协会原话**：「账号类处罚：由理事会审核后才生效，只给禁用账号开个小口子、只能看奖惩和提申诉」。
- **现行口径**：禁用账号**能登录**（照发 token），但只放行 `BannedAccountGate.EXEMPT_PATHS`（退出、奖惩记录、申诉、处置查看、站内提示）；**禁用态绝不能 logout**。审核时不因禁用而拒绝。
- **落点**：auth `BannedAccountGate`、`ensureLoginable` 只拒注销；honor `requireApprovableVolunteer` 撤回禁用拦截。
- **推翻**：8/10 版「禁用期间奖励、处罚都拒绝审核」的推论（理由未被推翻，手段从「不批」换成「让他够得到」）；因此 7️⃣-②「申诉期是否顺延」也随之消解。

### XH11 · 社区违规：宣传部审核即生效，用户照常申诉（申诉归理事会）
- **日期 / 原编号**：2026-08-11 处罚（3）（4）与第 6 条；2026-09-02 问题 6.2
- **协会原话**：「社区违规1：用户举报--宣传部审核--有违规则对其处罚，无违规则结束--审核即刻生效」「社区处罚：宣传部审核后直接生效，用户正常申诉」。
- **落点**：social 的举报与审核（V72），社区禁言挂 `honor:sanction-community` 那一档闸门（V71 起生效）。

### XH12 · 活动违规的两条来源：现场记录 / 用户举报 → 组织部审核定罚 → 理事会终审；组织部巡查发现 → 定罚 → 理事会终审
