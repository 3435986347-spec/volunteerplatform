# 后台控制台页面构建与功能新建

面向现有 `../volunteerplatform-back/`：无构建的 React，入口 `index.html` + `assets/*.js`，全部使用纯 `React.createElement`，只调后端 `/a/**`。本页规定**新页面怎么接进应用、完整功能按什么顺序做**；业务口径仍以[领域页](../领域/)和后端代码为准。

> **先分清应用**：这里是单组织实例的“后台管理控制台”，不是[领域十二的独立监管后台](../领域/12-监管后台.md)。后者是未建的平台级独立应用，有独立库、登录态和开工门禁；不要在现有控制台里加几个菜单就宣称实现了 SaaS 监管后台。

组件的历史坑与各批背景见[后台控制台](后台控制台.md)，本页只保留当前搭建契约。下文未特别说明的 `assets/`、`tests/` 路径均相对控制台仓库根。

> **所有前端共用的硬门禁**：[前端原型还原](前端原型还原.md)。新建或改结构前必须渲染并实际查看 PDF 对应页；原型图标先核对并提取原始资源。后台仍保留本地 SVG `Icon` 与既有色板，不直接搬用小程序 PNG。

## 1. 新建完整功能的流程

### 1.1 先定业务与归属

1. 读对应 `volunteerplatform-knowlegebase/领域/*.md` 的现行规则、功能状态、协会决策和需求出处；后台通用能力还要看 `volunteerplatform-knowlegebase/领域/11-后台管理系统.md`。
2. 明确操作者、可见范围、审核级数、状态何时生效、是否通知志愿者、是否产生积分／证书／处置等跨模块副作用。原型或上一版页面不能推翻协会最新口径。
3. 按后端模块边界确认 owner。改代码前读 `volunteerplatform-knowlegebase/模块/<模块>.md`；投诉建议归 data、帖子举报归 social、处置表归 auth 等既有归属不要因为“页面放在一起”而改动。
4. 先查现有页面和接口能否扩展。列表加筛选、详情加操作、独立新页面是三种不同改动，不默认新建菜单，也不把多条不同权限的审核线硬塞一页。

### 1.2 先冻结接口与权限契约

在写页面之前列出一张最小契约表：

| 项目 | 必须明确 |
|---|---|
| 场景与操作 | 列表、详情、创建、编辑、审核、状态变更、导入导出分别是什么 |
| URL 与方法 | 在 `volunteerplatform-knowlegebase/生成/接口/<模块>.md` 和 `文档/v1~v4/url文档v*.md` 核对；新端点遵循 `/a/<domain>/<resources>/{id?}/{action?}` |
| 权限 | 页面查看、按钮操作、待办计数分别使用哪个已登记权限点；新增权限点先后端迁移登记 |
| 数据形状 | Controller、DTO / VO 的必填字段、状态码、分页、字符串 Long、时间、金额和可空字段 |
| 写约束 | 幂等键、并发、重复提交、审核原因、软删除／恢复及操作日志是否由后端负责 |
| 验收边界 | 哪些能本地端到端，哪些依赖地图、对象存储、支付等外部渠道，不能提前宣称真实通过 |

接口文档与代码冲突时先确认实际后端实现；不要为了迎合旧前端去绕过后端现行规则。

### 1.3 后端先行或同步落地

若功能需要新后端能力，按根 `AGENTS.md` 与对应模块页完成 Controller / Service / DTO / VO、迁移和测试，再让控制台对齐真实实现：

- 新权限点不能只在 `NAV_GROUPS` 或按钮里写一个字符串；必须由后端迁移登记并真正鉴权。
- 新状态与魔法数由后端常量持有，前端做展示映射，不自行创造另一套业务状态。
- 改了 Controller、权限点或迁移后运行知识库生成脚本；改了后端行为先跑相应模块测试，不能只靠控制台页面验证。
- 新端点至少准备正常、空数据、校验失败、无权限和重复提交用例；涉及审核流时验证每一级真实效力。

### 1.4 再接控制台页面

按“领域 service（需要时）→ 页面组件 → 脚本加载 → 页面注册 → 菜单与标题 → 待办与概览”的顺序接线，具体见第 3 节。读取页面先跑通后再开放写按钮，避免每补一个操作就同时改多层、难以定位。

### 1.5 验收与收尾

1. 语法检查、全部 Node 契约测试、后端相应测试分别通过。
2. 用本地后端和测试账号在浏览器走真实读取与写入；至少覆盖有权、无权、空态、失败、重复点击和刷新。
3. 核对菜单、按钮、计数、接口权限一致，页面隐藏不等于后端鉴权。
4. 更新领域功能状态、模块现行要点和回归验证；新工作流必须有能证明它的用例。未做真实外部渠道验证要单列，不以 UI 完成替代端到端完成。

## 2. 视觉、色调与图标

### 2.1 当前视觉语言

`assets/styles.css` 是 Ant Design v5 风格的手工实现，使用 CSS 变量，不引入 AntD 运行包，也不套用小程序的粉色渐变。

| 用途 | 当前值 |
|---|---|
| 主色 / hover / active | `#1677ff` / `#4096ff` / `#0958d9` |
| 主色浅底 / 浅边框 | `#e6f4ff` / `#91caff` |
| 成功 / 警告 / 错误 | `#52c41a` / `#fa8c16` / `#ff4d4f` |
| 正文 / 次级 / 弱化文字 | `rgba(0,0,0,.88)` / `.65` / `.45` |
| 布局背景 / 容器背景 | `#f5f5f5` / `#ffffff` |
| 侧栏 | `#001529`，选中菜单使用主色 |
| 边框 / 分割 | `#d9d9d9` / `#f0f0f0` |
| 圆角 | 控件 6px、小标签 4px、卡片 8px |
| 控件高度 | 常规 32px、小 24px、大 40px |
| 字体与正文 | `FZDFS--GBK1-0` 优先，带系统中文字体回退；正文 14px、行高 1.5714 |
| 外壳 | 侧栏 232px、折叠 64px、顶栏 56px |

页面使用 `.page`，宽表格或管理页通常再加 `.page-wide`；内容区 padding 为 20px 24px 40px。优先写 `var(--primary)`、`var(--text-2)`、`var(--border-2)` 等变量，不在每个页面复制十六进制色值。主色派生由 `assets/app.js` 的 `applyPrimary` 统一处理，页面不要另写换色算法。

状态颜色必须表达业务语义：停用、历史、未生成等中性状态不一律用红色；审核通过、生效、待审等状态以 `MAPS` 或页面明确映射为准，不能只按文案猜颜色。

### 2.2 图标

- 使用 `assets/icons.js` 的 `Icon`，例如 `React.createElement(Icon, { name: 'edit', size: 16 })`。图标是本地 24×24 viewBox 的 SVG path 集合，通过 `window.ICONS` 暴露。
- 新增菜单先从现有 `ICONS` 选语义相符的图标；可用名覆盖导航、用户、活动、审核、文件、上传下载、警告、设置等。不要从 CDN 拉图标，也不要把小程序的 PNG 入口图标直接搬进后台。
- 确需新增时在 `ICONS` 增加唯一键，沿用现有描边、圆角线帽和 24×24 坐标；在 `Icon` 中用 `name` 引用，不在页面散落整段 SVG。
- 图标只是辅助，危险操作和审核按钮仍要有文字，不用无法辨认的图标替代操作名称。

## 3. 新页面的接线步骤

### 3.1 建页面与可选 service

1. 新建 `assets/page-<feature>.js`，页面组件名用唯一的 `Xxx_Page`。纯脚本没有模块隔离，顶层函数和变量会全局共存；新文件优先用 IIFE 包裹，只显式导出页面和需要测试的 service。
2. 多接口、复杂规范化或需要独立契约测试时，新建 `assets/admin-<domain>-service.js`，页面调用 service。简单页面可直接用 `API` 与 `ui-kit`，但不要为每个页面机械增加一层空 service。
3. 不引入 `import` / `export`、JSX、运行期 Babel、npm 打包、CDN React，也不复活 `assets/data.js` / `window.HD` mock。普通 `<script>` 的加载顺序就是依赖顺序。
4. 新工具函数使用领域前缀，避免与全局名或其他页面同名而静默覆盖。页面私函数不要无意挂到 `window`。

### 3.2 页面骨架

沿用现有结构：

```text
div.page.page-wide
  → PageHead（title / desc / actions）
  → Alert（需要解释业务限制时）
  → Card flush
  → Tabs（有状态页签时）
  → Toolbar（filters / actions）
  → Table（columns / data / loading / error / pagination）
```

- 列表用 `useKitPaged(path, query, opts)`，详情或设置用 `useKitGet(path, query, enabled)`。`useKitPaged` 会在查询条件变化时回第 1 页、丢弃迟到的旧响应，并兼容后端裸数组。
- `Table` 已提供 loading、empty、error 和分页；传 `onRetry` 让错误态能重试。自行渲染数组前仍需 `Array.isArray` 兜底，因为应用没有 error boundary。
- 编辑、审核和详情优先复用 Drawer / Modal；提交时 disable 相关按钮并用页面级锁或 `useRef` 防重，成功后刷新列表和详情。前端防重不代替后端幂等。
- 页面要解释真实业务限制，例如“初审何时生效”“为什么不能补发”“这里只是查询不是发证”。不要让操作者根据按钮名称猜副作用。

### 3.3 必须同步登记的位置

| 位置 | 要做什么 |
|---|---|
| `index.html` | 用普通 `<script src="assets/page-<feature>.js"></script>` 登记一次；service 在使用它的页面之前，所有页面在 `assets/app.js` 之前 |
| `assets/app.js` | 在 `PAGE_COMPONENTS` 增加 `pageKey: Xxx_Page`；使用 `window.Xxx_Page` 时保持现有导出约定 |
| `assets/shell.js` 的 `NAV_GROUPS` | 在合适的业务分组加入 `{ key, label, icon, code }`；`code` 数组表示任一权限可见，`null` 仅表示登录可见 |
| `assets/shell.js` 的 `PAGE_TITLES` | 登记标题和分组，供顶栏、面包屑及页面访问上报使用 |
| `assets/shell.js` 的 `TODO_SOURCES` | 仅确有“待处理队列”时登记 `{ path, query, countPerm }`；普通查询页不要造假待办 |

`pageKey` 在以上各处必须一致。菜单只加入 `NAV_GROUPS` 即可参与现有分组展开与收起；菜单排序／隐藏配置不替代权限检查。不要漏掉 `PAGE_COMPONENTS`，否则菜单看得到、页面却没有真实组件。

### 3.4 权限与待办

- 页面用 `hasPerm(identity, code)` 判定，按钮可用 `Auth` 包裹或操作项的 `show`；无权时可用 `kitNoPerm` 明说缺什么，不能返回一张让人误以为“没数据”的空表。
- 没有读取权限就不要发读取请求：`useKitPaged` / `useKitGet` 的 enabled 要受权限控制，待办计数同样只在有 `countPerm` 时请求。
- 页面入口、按钮和计数权限应与后端端点一致；仅靠菜单隐藏或 `Auth` 不是安全边界，后端仍必须鉴权。
- 待办计数只在 `TODO_SOURCES` 定义一次，侧栏与概览共用。一个菜单确有两个不同审核队列时可用 badge 数组，但不要合并不同角色的待办语义。
- 非 GET 成功后 `assets/api.js` 自动派发 `hd:mutated`，侧栏据此重数；页面自己的列表／详情仍需按交互刷新，不能假定角标事件替你更新所有数据。

## 4. 可复用组件与工具

### 4.1 基础组件

| 文件 | 可复用能力 |
|---|---|
| `assets/ui-core.js` | `Btn`、`Tag`、`StatusTag`、`MAPS`、`Avatar`、`UserCell`、`Field`、`Input`、`Textarea`、`Search`、`Select`、`RadioGroup`、`Checkbox`、`Switch`、`Card`、`PageHead`、`Toolbar`、`Tabs`、`Alert`、`Descriptions` |
| `assets/ui-overlay.js` | `Table`、`Pagination`、`EmptyState`、`LoadingState`、`ErrorState`、`Drawer`、`Modal`、`Dropdown`、`Steps`、`Timeline`、`Diff`、`Auth`、`AuditActions` |
| `assets/ui-upload.js` | `ImageField`、`CropModal`、`DropUpload`、`CROP_PRESETS` |
| `assets/ui-kit.js` | 分页／详情 hooks、行内操作、单元格、状态、确认、时间金额转换、幂等键、图片列表及选择器等 |

使用前读对应源码，当前特别容易漏错的契约：

- `PageHead` 的操作区 prop 是 `actions`；`Toolbar` 只渲染 `filters` / `actions`，不渲染 children。
- `Tag` 只认 `color`；状态映射优先复用 `MAPS`，页面自有映射可交给 `kitTag`。
- `Drawer.width` 只接受 `'wide'` / `'xwide'` 等既有约定；`Modal` 用 `wide`。两者的底部 prop 都叫 `footer`，传 `null` 才不显示底部。
- Drawer / Modal 已 portal 到 `document.body`，不要再套一层会破坏层叠的容器。
- `confirmDialog` 带原因时 resolve `{ ok, reason}`，不是字符串；通常直接用 `kitConfirm`。
- 行内操作使用 `kitActs`，两行单元格用 `kitCell`；不要在每页另造一套操作列间距。

### 4.2 数据工具

- `kitTime` / `kitDate` 做显示，`kitToInput` / `kitFromInput` 对接 `datetime-local`；不要用 UTC 的 `toISOString` 直接填本地时间。
- `kitYuan` 仅用于分转元展示，后端已有 `xxxYuan` 时优先使用后端字段；`kitFen` 用于输入元转分，避免浮点乘法误差。
- 后端要求幂等键时，每次打开新表单用 `kitRequestId` 生成，同一次提交重试沿用该键；提交成功或开始一笔新业务后再换，不能每次点击都换键。

## 5. 接口契约怎么对齐

### 5.1 请求入口

- 全部经 `assets/api.js` 的 `API`，不在页面直接 `fetch` 或手写 token／响应解包。
- `API.get(path, query)`；`API.post / put / patch / del` 都是 `(path, body, query)`。后端有必填 `@RequestBody` 时必须按 DTO 传 body，不能只传 query 或省略 body。
- 上传使用 `API.upload(file, dir)`，`dir` 必须在后端上传白名单并有相应权限；固定比例图片用 `ImageField`，普通多图可用 `KitImageList` / `KitImage`。
- 导出使用 `API.download(path, filename, query)`，它会带登录态并识别 JSON 错误；不要先 `window.open` 再当作已鉴权下载。
- 静默请求只用于页面访问上报等不影响当前操作的场景。正常业务失败要保留后端错误，不自动退回预览身份或 mock 成功。

### 5.2 字段与路径

| 项目 | 当前约定 |
|---|---|
| 路径 | `/a/...`，context-path `/api` 由基址处理；路径参数用字面量拼接，如 `'/a/x/' + id + '/status'` |
| 分页 | `page` 从 1 起、`size` 默认 10；分页读取 `records` / `total`，但允许后端明确返回裸数组 |
| ID / Long | ID 保持字符串，不因 `input type=number` 或比较而损失精度；仅确定安全的计数可转 Number |
| 时间 | 响应为 `yyyy-MM-dd HH:mm:ss`，入参兼容空格与 ISO `T` |
| 权限错误 | 401 才清会话；403 是当前操作拒绝，不登出、不换 mock 身份 |
| 隐私与安全 | 信任后端的可见范围和脱敏结果；图片／链接仍校验可用来源，不把用户输入直接当 HTML 注入 |

契约测试依赖从字面量路径还原端点。不要先把路径塞进通用变量再调用，导致扫描漏掉；`TODO_SOURCES` 这类声明式路径由专门规则核对。

### 5.3 本地联调红线

本地直接打开 `index.html` 时 API 基址会指向线上后端。联调统一使用文档仓库的 `tools/serve_admin_local.py`，它只在响应里改写到本地后端，不修改源文件。任何写操作前确认当前基址确为本地；不要为了联调把正式 `index.html` 的基址改掉并提交。

## 6. 测试、浏览器验收与交付

### 6.1 自动检查

```bash
node --check assets/page-<feature>.js
node --test 'tests/*.test.js'
```

- 页面／脚本注册参考 `tests/admin-wave-registration.test.js`：脚本只加载一次、依赖顺序正确、文件真实存在。
- `tests/admin-api-contract.test.js` 核对 `/a` 方法与路径、必填请求体、权限点种子、上传目录白名单；拿不到后端源码时部分用例会跳过，**跳过不等于契约通过**。必要时用 `HD_BACKEND_DIR` 指向实际后端源码。
- 为页面增加针对本功能的测试：权限显隐、禁用与防重、状态映射、字段转换、刷新和迟到响应，不以“全量旧测试绿”代替新功能测试。
- 改了后端 Controller 还要在文档仓库运行 URL 契约和知识库生成／校验脚本；前端 Node 测试不能替代后端测试。

### 6.2 浏览器真实验收

1. 用本地 MySQL、Redis、api 与 `tools/serve_admin_local.py`，准备有权与无权测试账号。
2. 从真实登录开始，核对菜单、直接导航、页面标题和页面组件都可达；无权账号不发越权请求。
3. 走“列表 → 详情 → 新增／编辑／审核 → 列表与详情刷新 → 待办角标变化”的完整路径；检查网络请求的方法、路径、query 和 body。
4. 覆盖空数据、接口失败、长文本、宽表格、窄窗口、抽屉／弹窗层级、连续点击、上传失败和导出错误。
5. 语法通过、浏览器渲染、请求契约、真实业务生效是四个不同层次。地图、支付、对象存储等未接真实渠道时，交付记录必须明确保留限制。
