### 为什么此刻规划 V3

V2 第 5 批（奖惩中心）代码已收口（V32–V38、13 端点、5 权限点），**唯一真正卡住的是协会问题二**——
活动类处罚是一级还是两级审核。它挡着「按处罚域拆部门权限」那**一件事**：一级只需按处罚域分开
「谁能开单」；两级要新增「已初审、待终审」状态，通知、申诉期起算点、后台待办数字全跟着变，
**两种数据结构不一样，选错要返工**，所以答复前不动。

问题一（微信推送走服务号还是订阅消息 + 两条缺失模板）挡的是推送渠道；问题三/四/五都不阻塞。
**第 5 批只剩这一个待解锁的小改动，不值得整条线等着它**，故本轮规划 V3。

⚠️ **V2 遗留的问题一～五继续挂在 `文档/v2/`，不搬进 V3**：问题二解锁后是一次与 V3 任何批次
都无耦合的独立小改动；问题四（投诉建议默认部门）属 `data`，不在 V3；问题五（注销后是否发短信）
已按推论实现，V3 新增通知沿用同一口径（承重条款 6）。

## 三、核心设计判断 D1–D8

> **编号约定**（防指错）：设计点 **D1–D8** · 需求洞 **洞1–洞4** · 协会清单 **①–⑯** · **批次用名不用号**。
> 早期版本里设计点与协会清单同用 ①—，`⑦` 在两处都存在，漏一次前缀就指错。

### D1　trade 的依赖方向——「只依赖 common」在第一个管理端接口上就破了

`/a/trade/orders/{id}/refund` 必须记操作人，而 `StpAdminUtil` 在 auth。
同时 **Row 5 会员费**（原文「需要预留个门，比如说注册几年，一年收多少钱会员费」）是 **auth 域**的事：
若 trade → auth，日后 auth 要查缴费状态就**成环**。

**取 (c)**，另两条一并留在这里、不删——依赖方向是最容易被「顺手改一下」破坏的东西：

| | 做法 | 代价 |
|---|---|---|
| **(c) 取** | trade 保持 common-only，`/a/trade/*` 与两条 webhook 的控制器**放 api**，trade 的 service 收 `operatorId` | 零重构、不成环。先例：api 的 `FileUploadController` 就是「api 控制器 + `StpAdminUtil`」 |
| (a) | 把 `StpAdminUtil` 挪进 common | 要给 common 加 sa-token 依赖，并改所有引用模块 |
| (b) | trade → auth | 今天零成本，但把会员费逼进新模块，且成环风险只是推迟 |

⚠️ **(c) 的先例只覆盖一半**：api 控制器用 `StpAdminUtil.STP_LOGIC.checkPermission` 是现成的，
**但没有任何 api 控制器取过操作人 id**（全 api 只有 `SaTokenConfigure:117` 取过）。
所以 (c) **必须配两条写死的规矩**，否则下一个人会在 trade 里建 controller、为取 `operatorId`
顺手加 auth 依赖，**(c) 就无声退化成 (b)**：

1. **trade 模块不放 controller**——`/a/trade/*` 与两条 webhook 一律在 api；
   trade 的 service 一律收 `operatorId` 并**硬校验非空**（沿用 `ActivityChangeService` 那条既有边界口径）。
2. **验签与解密必须在 trade 的 service 内**，api 控制器只做「读原始报文 + 转发」。
   (c) 的连带风险正是把支付逻辑养到 api 里去——api 的定位是启动类 + 全局配置 + 聚合接口，
   webhook 验签一旦落在那儿，下一段状态机也会跟着落过去。

### D2　支付成功怎么回到业务域——trade 唯一真正难的地方

方向是通的：`AttendanceConfirmedEvent`（activity 发、honor 听）已有先例，trade 发事件、donate 听，
依赖方向正好。**但那个先例的教训必须一起搬**：Spring 事件是**进程内、不持久**的，所以才有
`CertificateReconcileJob` 兜底。

**证书丢一次事件只是少一张证书；支付丢一次事件是钱收了、单没发货。**

所以 trade 批的**完成定义包含四道**，缺一不可：

1. 业务状态迁移**幂等且可被重复驱动**——回调、主动查单、扫描任务**三条路走同一个方法**；
2. **分钟级扫描**捞「已发起未终态」的单去主动查单（「每日对账」对付款失联太慢）；
3. **每日对账是第四道，不是唯一那道**；
4. 上面三道各有用例，且回调用例覆盖**重复投递 / 乱序投递 / 金额不符**。

### D3　`PickupCodeService` 落 common 做不了 CAS 核销

common **零 Mapper、零 `@TableName`**；而 CAS 核销必须知道往哪张表
`UPDATE ... WHERE pickup_code = ? AND status = ?`——商城单与纸质申请单是**两张表**。

V2 说的「共用一套、别造第二套」（`V2规划.md:922`）落成：

- **common 出无状态的三件**：码生成、格式校验、Code128 渲染（形态照 `constant/AttendanceQr`
  的单一来源常量 + `QrCodeUtil`）；
- **各域自己对自己的表做 CAS、各自建 `uk_pickup_code`**。

**共用的是码的形态与生成，不是一张共享表。** 这个区分要写在实施前，否则会卡在 common 里。

### D4　退分为什么用 `EXCHANGE` 而不是新分配来源码

`PointSourceType` 的 javadoc 明写「**新增来源必须分配新码，不要复用**」——后人照着教条改是大概率事件，
所以理由必须写准：

**不是因为 `source_id` 被占住了**（那只解释了为什么退分要走 `requestId`）。
**真正的理由是口径**：退分若用新的**非消费类**来源码，`totalSpent` 会停在 10、`totalEarned` 反而 +10，
「已使用积分」与「累计获得」**同时算错**，排行榜（排累计获得）跟着错。
用 `EXCHANGE` 记正数，净额自动归零。

落地：退分走 `requestId = sys:mall-refund:{orderId}`，在 `PointSourceType` 新增**系统保留前缀常量**，
`PointService` 对非兑换来源拒绝该前缀——与 `REVERT_REQUEST_PREFIX` 完全同形状
（含 `REQUEST_ID_PATTERN` 的 ASCII 限制与 V34 的 `utf8mb4_0900_bin`）。

⚠️ **这段话必须同时写进本文档和 `PointSourceType` 的常量注释。**

### D5　负余额检查与锁是「要做的抽取」，不是现成的

`PointService.java:354` 的锁与 `:361-365` 的余额检查**都只在 `adjust()` 里**，
`record()` 本身既不加锁也不查余额。抽取时两件承重：

- 锁键必须是**同一把** `lock:point:volunteer:{id}`——换个前缀，「手工扣分与兑换互斥」这条不变式就没了；
- 锁必须**包住整个订单事务**，不是在事务内取（项目既有约定）。

### D6　库存回滚的幂等

驳回/取消要还库存，而双击驳回、回调重投都可能还两次。与退分同形：
**订单状态 CAS 成功才还，且还库存与退分同事务。**

### D7　勋章的两条判例：(a) 直接照抄，(b) **不能无条件照抄**

这两条只在并发与「先查再动作」的窗口里现形，**顺序调用的用例永远绿**，不写下来实施时几乎必然复现。

#### (a) 改已过审 / 已上架的商品，必须退回待审

`MedalService:73` 原话：改完还算「审核通过」等于给了一条绕过审核的路——
**先提交一版素净的过审，通过后再改成别的，样式审核形同虚设**。
商城的后果更实：改的是**价格、所需积分、赞助方**。

连带两条一并抄：

- 限制**写进 UPDATE 的 WHERE**、靠影响行数判定（`:106` 的 `.ne(status, PENDING)`）——
  只在方法开头 `if` 拦不住「修改先完成、审核后完成」，那个 `if` 读的是 RR 快照；
- **纯展示字段（排序、隐藏）走独立入口，不触发重审**（`:188` 的 `updateSort`）。

#### (b) 下单时怎么取商品与规格——判据是「读完之后改不改这一行」

⚠️ **本规划早期版本在这里写错过，是纪律性错误，故留下反面案例**：
曾写成「下单取商品/**规格**用 `FOR SHARE`，不用 `FOR UPDATE`」。

- 对**商品头**是对的：只做上架 / 隐藏 / 卷要求的**比对**，不改那一行；
- 对**规格行是错的**：规格行读完**紧接着就是库存 CAS** `UPDATE ... SET stock = stock - ?`。
  两个人同时买同一规格会各自先拿 S 再一起抢 X——**正是 `RewardPunishService.java:403`
  写死过的锁升级死锁**（「先 S 后 X 是锁升级，两名管理员同时审同一个人的两张单会直接死锁」），
  `MedalService.delete:167` 因此取的是 `selectByIdForUpdate`。

勋章判例 (b) 能用 S，是因为 `requireMedalForShare` 读完**只比对、不改那一行**（改的是发放记录）。

**修法（取第一条）——把上架 / 未隐藏 / 未删除折进库存 CAS 的 WHERE，一条语句，根本不产生锁升级：**

```sql
UPDATE mall_goods_spec s JOIN mall_goods g ON g.id = s.goods_id
   SET s.stock = s.stock - ?
 WHERE s.id = ? AND s.is_deleted = 0 AND s.stock >= ?
   AND g.status = 上架 AND g.hidden = 0 AND g.is_deleted = 0
```

按影响行数判定；0 行时**再补一次只读查询**区分「无货」还是「已下架」，给出准确文案。

⚠️ **两个 `is_deleted` 都要显式写。** `@TableLogic` 挂在 `BaseEntity:45`，
**只对 MyBatis-Plus 自己生成的语句与 wrapper 生效**，手写 `@Update` 不会自动补——
漏掉 `s.is_deleted = 0`，软删的规格照样能被扣库存下单。
这与证书样本那条「软删行仍占唯一键、管理员删了就再也建不出同作用域的新样本」是**同一族**：
**软删在手写 SQL 里永远要显式处理。**

**备选（若坚持先读后改）**：**规格行 `FOR UPDATE`、商品头 `FOR SHARE`**，
且**获取顺序固定为先头后规格**——否则两把锁在不同路径上顺序不一致，又是一类死锁。

⚠️ **这条纪律永远写成带判据的版本**：「**读完之后改不改这一行**：只读比对用共享锁，
真读改写才用排他锁」。只写「用 `FOR SHARE` 不用 `FOR UPDATE`」会被下一处照抄——上面那次就是这么错的。

### D8　`mall_order` 必须快照商品名 / 规格名 / 所需积分

与勋章「附带积分**取发起时快照**而非审核时现读」、纸质证书「自提点存**快照文本**、不是悬空 id」同源：
规格可改可删，事后要还原得出**当时买的是什么、花了多少分**。
既然引入了 `mall_goods_spec`，这条就必须同批写，否则删一个规格，历史订单就成了空壳。

### 商城批（V41 起）

表：`mall_goods` / `mall_goods_spec` / `mall_goods_review` / `mall_order`。
**单商品订单，不建 item 表**——原型没有购物车（购物车是纸质证书 P84 那条线，属 honor）；
日后要多商品是**加 item 表**，不是改单头。

范围：商品 CRUD 与审核（**照抄 D7(a)**）、隐藏、**库存 CAS 用 D7(b) 的 JOIN 单语句**、
下单（**快照商品名 / 规格名 / 所需积分**，D8）、扣分、自提取货码与核销（D3）、我的兑换、
商品评价（**带资格闸门**）、兑换记录、兑换规则图文。

**下单即扣分、驳回 / 取消退分**——与奖惩「审核通过才入账」**刻意相反**：
那里是**罚**，这里是**用户主动消费**，积分与库存都必须占位，否则同一笔积分能下十张待审单。
⚠️ **这条理由必须写进代码注释**，否则日后会被当成不一致而「统一」掉。

**一单一件（数量恒为 1）**——Row 8 的兑换列表与「我的兑换」都没有数量控件，
原型也没有购物车，故 qty=1 是站得住的默认。⚠️ **但这是取舍，不是「还没做」**：
要加数量，`stock - 1` / `stock + 1` 的库存 CAS、订单表、D8 的三项快照（「花了多少分」不再等于规格单价）、
退分金额**四处必须同时改**，而其中只有 SQL 里那个 `1` 会在改的时候撞到眼前。
**写在这里就是为了让另外三处也被想起来**；`MallGoodsSpecMapper.deductStock` 与
`MallOrderService` 的类注释各留一句指回本节。

短信接 `POINTS_ORDER_REVIEW`（已报备），走 `SmsNotifyService`，**不手拼 Map**。

**还库存的影响行数不丢**（`restoreStock` 返 0 有两种原因）：规格**已软删**是正常运营——
软删后 `deductStock` 再也扣不到它，库存数字已无消费方，不还就对了；规格**根本不存在**
则是数据完整性问题（本表无外键，订单可以挂着一个不存在的 specId 落库）。
两者都无声的话，后者永远没人知道，故 0 行要记日志并区分是哪一种（`selectDeletedFlag`，
它绕过 `@TableLogic` 才看得见软删行）。**但不抛异常**——抛了会连退分一起回滚，
志愿者会因为管理员删过一个规格而永远取消不了单。与「通知失败绝不影响业务」同一条取舍：
代价是它在线上只留一行日志，所以那行日志必须说得清是哪一种。

**取货码落地形态（D3 的实现口径）**：common 出的是 `pickup/PickupCodeUtil` + `qrcode/BarcodeUtil`，
**命名是 `Util` 不是 `Service`，刻意的**——`Service` 会招人往里注入 Mapper，而 D3 的整条边界就是
「common 不碰表」。码形 `PU` + **域标记** + 10 位随机（32 字符表去掉 `0 1 I O`）：
去掉那四个字符使输入侧<b>不需要任何纠错映射</b>；域标记（`M` 商城 / `C` 纸质证书）让两个域
**共用码空间却不可能撞**，也让「拿证书的码到商城柜台」当场被拒而不是查一趟再报查无此单。
随机源是 `SecureRandom` 而非订单号那样的 `ThreadLocalRandom`——**取货码是柜台上的持有者凭据**，
可预测就等于谁都能领走别人的东西。

**核销按码不按 id**（`POST /a/donate/orders/verify`，与骨架里写的 `/orders/{id}/verify` 不同）：
扫码枪扫出来的是码。做成按 id 会逼前端先按码查一次 id，多一次往返，还把一个本可原子的动作拆成两步。

权限点：`donate:goods` / `donate:goods-audit` / `donate:order` / `donate:order-audit` / `donate:verify`。

**兑换规则（Row 8 C 文字 + 图片）＝ 单行表 `mall_exchange_rule`（V42）**，三条路里选的第二条：

- **不用配置项**——自提点走配置是因为它是<b>运营常量</b>且要下单快照；兑换规则是<b>内容</b>，
  协会会改、会随活动调整，放配置项意味着改一句文案要重启服务。两者形似而性质相反。
- **不复用 publicity 公告**——公告流会把它列进去，要排除就得给公告加标记列（**同样要迁移**），
  还把商城概念漏进 publicity，且有人删掉那条公告会让商城页面静默变空。省不下迁移，
  却买来一处跨域耦合。

落地四点：① 固定 `id=1`，迁移里就把行建出来，写入走 `INSERT ... ON DUPLICATE KEY UPDATE`
（「先查再决定 insert 还是 update」并发下会一个插入一个撞键）；② **不做上下架 / 多版本 /
生效时间**——Row 8 只要「一份当前规则」，加状态位是替协会做决定，与「原型已经答过的别写成
待决策」是同一条纪律的反面：**需求没提的别自己发明**；③ **权限点复用 `donate:goods`，不新增**
（仍 56 个），理由记在 `PermissionCode` 上；④ 图片走 `/a/files/upload?dir=exchange-rule`
——`FileUploadController` 在 **api 模块**、按 dir 双门槛（权限 + 类型），
**改商城的人不会顺手打开它，这处最容易漏**。

`images` 在库里**换行分隔**而非逗号：URL 可以合法地含逗号、不可能含换行
（`service_guarantees` 用逗号是因为那存的是固定 key）；不引 JSON 库是因为 fastjson2
只在父 POM 的 dependencyManagement 里声明过、**全项目零引用**。代价是写入侧必须逐个校验
URL 不含换行，否则一条 URL 会被切成两条指向别处的碎片。

### 捐书批（最重，约等于两批）

10 步流程 + 三级条码（物品 / 箱 / 运单）+ 不合格退回 + Row 17 F 的 10 维搜索与导出。
表：`donate_campaign` / `donate_shipment` / `donate_item` / `donate_box` / `donate_item_trace` /
`donate_barcode_catalog`（Row 17 D 的商品条码库）。

- 三类条码前缀收一个持有类（仿 `constant/AttendanceQr` 的单一来源）；
- 每个扫码动作（到货 / 核对 / 装箱 / 出箱 / 送达）**CAS + 留痕**；**轨迹对捐赠人公开**是原文要求；
- `LogisticsService`（快递100）**本批只出查询**（轮询 + 轨迹**快照落库**，外部不可用时页面仍要能看）。

⚠️ **轮询必须有终态停止条件**：已签收 / 已退回的运单**退出待办集合**，
否则扫描集合随历史单量单调增长——与 V39 `idx_reminder_pending(reminder_sent_time, start_time)` 同形，
扫描条件要能走索引。

⚠️ 本批全是扫码动作、V3 又不做前端，**连手工验证的路径都没有**。除「接口按**一次一个扫码动作**的
粒度设计，不要设计成批量表单」外，**完成定义里加一个内部用的扫码测试页或脚本**，
否则 API 形态没有任何反馈来源。

### 微心愿批

复用捐书批的物资流转（认领 → 录入物资 → 包裹 → 到货 → 核对 → 专属条码 → 反馈图片）。
本批独有的三件：

- **受助人是未成年人**：姓名 / 性别 / 年龄 / 学校 / 年级属 PII，复用 `CryptoUtil` 密文存储；
  「认领前打 `*`、认领后显示全部资料」的**授权判定必须落服务端**，不能靠前端不显示；
- **两道门**（洞4）：须**实名志愿者**才能认领、须**已验手机号**才能查看——后者独立于登录态；
- **认领占位**用生成列唯一键（仿 V9 `uk_active_volunteer` / V28 `uk_active_grant`），取消认领即释放。

本批后**放行 `rank_type = 4`**。⚠️ 按 CLAUDE.md 的常设规矩（「排行榜口径只认 activity 的
`ActivityRankingQueryService`，不要在 honor 域自己拼 where」），**donate 必须出一个同形态的只读服务
`DonateRankingQueryService`**，honor 只排序、定名次、存快照。
「什么算圆了一个心愿」见清单 ⑯，默认取**送达 / 已实现**（认领可取消，按认领算会让榜单反复抖动）。

**✅ 已落地（2026-09-16，V51）**——以上三件都按原样实现，另有三条落地时才定的口径，记在这里免得日后当成漏做：

- **`biz_id` 挂在「认领」上而不是心愿上**：认领会被取消、心愿会被别人重新认领，挂在心愿上就分不清
  「这一包是谁寄给这个心愿的」；
- **能不能取消 / 撤销认领，按「物资还活着吗」判**（在途 / 待核对 / 合格 / 已送达），不按「有没有运单」判——
  一包东西全被判不合格时它对心愿已经没用了，按运单数判会让认领人永远取消不了；
- **撤销认领与心愿实现只发站内提示，没有短信**：协会 2026-08-11 报备的 20 条通知模板里**没有微心愿这一类**，
  而通知短信只能走 `SmsNotifyTemplate` 已登记的模板（现编模板键等于发不出去还不报错）。
  协会若要短信，先报备模板、再在枚举里登记，业务侧只加一行。

### 结对批

助学助困的结对项目、指定金额或全款的**认领登记**、受助方**写信板块**（图文）；
众筹的**项目管理**（全部 / 进行中 / 已结束）与进度展示。**全程不碰支付。**

⚠️ **证书在本批只做「权益与渲染」那一半。** 把「捐赠后自动生成证书」整条放进无支付批是矛盾的——
捐款在捐款批，那出证由什么触发？本批只做：

- 新增证书 `type` + **生成列幂等键** + 接入 honor V31 渲染链（样本套印 + 懒渲染 + 短期签名 URL）+ 迁移；
- 迁移里必须确认两件事：`ck_cert_activity_scope` **只约束 `type = 1`**（新 type 不受影响）；
  `uk_slot_cert(type, volunteer_id, slot_id)` 对 `slot_id IS NULL` **防不了重**
  （MySQL 唯一索引视多个 NULL 互不相同），所以捐赠证书必须另设生成列幂等键。

**「支付成功即出证」的挂钩留在捐款批。** ⚠️ 这也是清单 ⑨ 的延伸：
「结对成立就出证」和「钱到账才出证」是**两种承诺**，一并问清。

**✅ 已落地（2026-09-16，V52 / V53 / V54）**——按上面的范围实现，另有几条落地时才定的口径，记在这里免得日后当成漏做或当成需求：

- **金额列叫 `pledged_amount`（认捐额）不叫 `raised`**：本批没有支付，系统并不知道钱有没有到账。
  叫 raised 会让前端把一个没到账的数当成「已筹到的钱」展示给捐赠人，那是会被追责的失真；
  众筹的 `raised_amount`（到账额）建了列但恒为 0，由捐款批写入。
- **认捐额的上限写在累加语句里**：登记时校验的是「当时的缺口」，而认捐额在<b>确认成立</b>时才累加——
  两个人各自登记了不超过缺口的金额、两笔都确认，加起来就越过了受助金额。并发用例撞出来的。
- **参加人数不存列**，按有效登记现算（存列就有两个口径，本项目为此栽过三次）。
- **本批不建受助人 PII 列**：Row 10 只要求展示项目图片、金额与进度，没有要求展示受助人姓名 / 学校。
  微心愿那边建密文列是因为 Row 12 明确要展示并打 `*`；这里没有那条需求。
- **捐赠证书的幂等键另起**：`uk_slot_cert` 对它不起作用（没有场次，多个 NULL 互不相同），
  改用 `biz_ref = pair:{结对登记id}` + 生成列唯一键 `uk_cert_biz_ref`（V54），软删行仍占键（与活动证书同口径）。
- **出证走领域事件**：依赖方向自微心愿批起是 `honor → donate`，donate 不能反向调用，
  故 `PairEstablishedEvent` / `PairCancelledEvent` 由 donate 发、honor 订阅（`AFTER_COMMIT`），
  与 activity 的 `AttendanceConfirmedEvent` 完全同形。
- **取消已成立的结对会撤销证书**（软删、留原因、可恢复）——否则留下的是一张为不存在的结对盖章的证书。
- **捐赠证书没有定时补偿**（活动证书那条线有 `CertificateReconcileJob`）：扫描口径、回看窗口与
  「历史数据要不要补」都得先有协会口径，而那正是活动证书那边吃过亏的地方。人工救济是
  `POST /a/honor/certificates/pairs/{pairRecordId}`（幂等）。
- **样本仍取「缺样本就拒绝出证」**：协会现有样本只有活动证书那一张（清单 ⑨ 未答），
  捐赠证书先找 `donate-pair` 作用域、退回 `global`；都没有就拒绝，不退回自绘无章版式。

### trade 批

表：`trade_order`（bizType + bizNo + 金额快照 + 状态 + 过期时间 + out_trade_no）/ `trade_payment` /
`trade_refund`；`uk_biz(biz_type, biz_no)` + `uk_out_trade_no`。

- 回调**验签 + 解密**（APIv3 平台证书），端点 `/callback/trade/wechat/pay`、`/refund`——
  **无角色前缀**：靠验签而非登录态。⚠️ 机制说准一点——拦截器注册在 `/**` 上，只是处理器内部只对`/v/**` `/a/**` `/e/**` 做 `check`，别的路径落不到 `check` 上才得以放行；日后谁加一条全局 `match("/**")` 就会把 webhook 变成 401，故这件事要由用例钉住；
  完整地址含 context-path `/api`，nginx 的 `location /api/` 已覆盖；
- **必须拿回调金额与本地单比对，不符一律拒绝并告警**；
- **状态以主动查单为准**（本地与微信不一致时以查单结果为准）；
- **TTL 默认 15 分钟，各 `bizType` 可覆盖**——商城占库存用 15 分钟合理，
  **众筹捐款不占任何资源，15 分钟关单只会平白打断捐赠**；
- **退款粒度默认整单**（V3 自己的口径，非协会已答，见清单 ⑭）；
- 业务回写四道见 **D2**。

⚠️ **可验证性边界**：没有商户资质与备案域名，回调段**无法端到端验证**，
测试只能到「本地状态机 + 模拟回调报文 + 验签」为止。
**别把「用例全绿」当成「支付通了」。**

**落地记录（2026-09-17）**——与上面规划有出入或规划没写到的，逐条记下：

- **唯一键不是 `uk_biz(biz_type, biz_no)`，是生成列 `uk_active_biz`**：那是简写，真按它建，
  订单超时关闭之后同一笔业务**再也付不了第二次**（微信要求关单后换新单号重下）。
  故只在待支付 / 已支付时占键，关闭 / 退款后释放（同 V9 / V52 的写法）。
- **金额一律存「分」（INT）**，与渠道一致；业务侧（结对认捐、众筹目标）存 DECIMAL 元，
  **换算只在调用方进 trade 的那一刻发生一次**，不让两套单位在系统里并存。
- **已关闭的单收到支付**（关单边界上付款、后台关单后渠道关单失败）：钱是真收了——
  流水照记、状态不改、打 ERROR；**这行 ERROR 的出口是每日对账**（对账核「已关闭」那一侧，差异落库）。
  只核已支付的单永远看不见它，规划里没写到这一侧，是实现时补的。
- **对账每一次都落库**（`trade_reconcile_run`），渠道未开通时也落一行 `skipped=1`——
  「今天没有对过」本身要让人看到；只写日志等于把「钱收了、单没发货」变成一条没人读的日志。
  后台 `GET /a/trade/reconciliations?onlyMismatch=true`。⚠️ **停机跨过凌晨那次执行，那一天不会自动补**，
  列表按日期看得出缺口，用 `POST /a/trade/reconciliations` 手动补。
- **应答语义**：处理完（含重复投递）回 200 SUCCESS；**验签失败 / 金额不符 / 单号不认识回 500 FAIL**——
  回 SUCCESS 等于把一次可疑投递藏起来，而渠道的重投正是我们要的第二次机会。
- **webhook 读原始字节流**，不用 `@RequestBody String`（见执行状态表第 7 行 ①）。验签算的正是这串原文。
- **Sa-Token 放行机制已由用例钉住**（`TradeCallbackApiTest`）：它同时反向断言「不带 token 打 `/a/**` 必须 401」，
  这条反向断言撞出了执行状态表第 7 行 ③ 那个全项目级缺陷。
- **退款**：事务内先把额度占住（`addRefunded`，上限写在 UPDATE 的 WHERE 里）并落「处理中」，
  渠道调用在事务外；渠道拒绝 / 未开通即置失败并释放额度；结果回写幂等。
- **`TradePaidEvent` / `TradeRefundedEvent` 本批没有消费方**——商城快递批与捐款批接。
- **仍未验证的**：`WechatPaymentGateway` 那一层（APIv3 签名、平台证书、`createOrderV3` / `queryOrderV3` /
  回调解密）只在编译期对过 wx-java 的方法签名，一次真实调用都没有发生过。商户资质下来后，
  第一件事是用 1 分钱走一遍「下单 → 付款 → 回调 → 查单 → 退款 → 对账」。

### 物流推送批（有迁移）

订阅推送要记「**哪张运单已经订阅过**」，否则重启、重投、重跑都会重复订阅，**而订阅是付费项**。
这与 V39 `activity_slot.reminder_sent_time` 同形：

- 幂等依据**落库不放 Redis**——Redis 被清一次会让全部历史重新订阅一遍，那是真金白银；
- 记在**正确的粒度**上——那里是**场次**，这里是**运单**。

故至少一列 `donate_shipment.subscribe_time` + 一条「待订阅」可走的索引。

**落地记录（2026-09-17，V56）**——与上面规划有出入或规划没写到的：

- **一列不够，落了七列**：`subscribe_status`（五档）/ `subscribe_salt` / `subscribe_attempts` / `subscribe_attempt_time` /
  `subscribe_time` / `subscribe_error` / `push_time`，索引 `idx_subscribe_pending(subscribe_status, track_done, subscribe_attempt_time)`。
  只记「订阅时间」分不清「订过但被拒」「被快递100 中止」「失败还在重试」，而这三种要做的事不一样。
- **先占住、再发请求**（`claimSubscribe` 影响行数为 1 才调快递100），顺序与 V39 提醒同形：宁可这一轮漏订（下一轮还会捞到），不可重订。
- **返回码分流**：`200` 受理；**`501` 重复订阅也算受理**（上一次其实订上了、只是应答丢了）；
  `700/701/702`（快递公司 / 单号被拒）直接放弃；其余按可重试——**`600/601` 授权 key 错误也按可重试**，
  key 配错是整批的问题，改好配置后这些运单还应该订得上，不该每一单都被判死。失败满 `max-attempts` 放弃。
- **放弃与被中止都交还轮询**：订阅这条路走不通时，捐书批那条查询链路照常兜底；
  反过来，**订阅中的运单轮询跳过、志愿者查看也不按次查询**（订阅与查询各付一份钱），后台 `refresh=true` 不受限——推送卡住时那是唯一的手动出口。
- **salt 每单一个、首次生成后不再换**：全局一个 salt 泄露即可伪造全部运单的推送；重试时换 salt 会让「其实上次订上了」的那张单永远验不过。
  回调地址带 `?sid=运单id`，验签就用那一单的 salt，且推送里的单号必须与运单一致。
- **乱序保护写在 UPDATE 的 WHERE 里**：快递100 每次推全量轨迹，但会重推、会乱序；只在新快照的最新节点不早于库里那条时才写。
  状态迁移同理只朝前走：迟到的 `polling` 不能把 `shutdown` / `abort` 拉回「订阅中」。
- **未订阅过的运单收到推送回成功**：它没有 salt、验不了签，也改不了任何东西，让快递100 一直重推只会刷满日志。
- **订阅不在「登记寄出」请求里同步发起**，由每 5 分钟的任务发起：那样会把一次计费、可能超时的外部调用挂进捐赠人的提交。
- **捐书批两处遗漏同批补上**：微心愿运单查轨迹时收件电话是空的（顺丰要求电话），改取 `hengde.donate.wish.recv-phone`；
  快递100 的配置项（查询与推送）补进 api 的 yaml 与 `部署/api.env.example`，`ProductionConfigGuard` 对「推送开了但 key 或 https 回调地址缺失」启动即拦。
- ⚠️ **可验证性边界**同 trade 批：真实推送要备案域名，本批测到「假快递100 + 模拟推送报文 + HTTP 表单验签」为止。

### 商城快递批

快递费**计价器**（沿用 V2 第 4 批定下的「应付金额 = 计价器输出，**不是常量**」）；
两条路——**现金走 trade**、**积分抵扣走 `PointService` 并入订单那一笔**（否则撞 `uk_source`，见 D4）。

**落地记录（2026-09-17，V57 / V58）**——与规划有出入或规划没写到的：

- **商品现金部分（清单②默认 (甲)）同批落地**：规格上 `cash_fen`，下单快照 `goods_cash_fen`；应付现金 = 商品现金 +（现金付快递费时的）快递费。
  改现金部分与改积分一样退回重审（`MallGoodsService.update` 的 CASE 已覆盖整次修改）。
- **待支付（status 5）占着积分、库存与卷**——与「下单即扣分」同一口径：付款之前不占，同一件东西能被十个人同时卡在付款页。
  代价是付款截止（默认 15 分钟，`pay_expire_time`）+ 补偿任务；**截止同时传给 trade**（`CreateOrder.expireAt`），交易单不会比兑换单活得久。
- **微信支付没开通时，需要现金的单在下单那一刻就拒绝**，不落一张付不了的待支付单——它会占着库存等超时，别人也兑不到。
  积分抵扣快递费不需要商户资质，**现在就能从下单一路走到签收**（`MallExpressApiFlowTest` 走的正是真实部署形态）。
- **取消与付款不能两边都赢**：取消先让 trade `closeByBiz`，关不掉（已付）就放弃取消；发起付款与取消**持同一把志愿者锁**
  （`lock:point:volunteer:`），不会出现「刚关掉旧交易单、付款又建了一张新的」。`MallExpressConcurrencyTest` 对「取消 vs 回调」「超时同步 vs 回调」各跑 30 轮、偏置起跑、断言两种结局都出现且每轮账对得上。
- **付款成功的推进不只靠事件**：`TradePaidEvent` 只发一次、不持久；`MallOrderSyncJob` 每 2 分钟拿待支付的单去问 trade——
  已付的推进，过期的先让 trade 以渠道为准查一次，渠道说没付才关单取消。
- **已付款的单志愿者不能自己取消**（清单⑰默认）：退现金要走原路退款、trade 的退款要记后台操作人，让一个按钮就把钱退出去不妥。
  由协会驳回：**先 CAS 驳回并归还积分库存卷、提交之后再发起退款**——反过来，退款成功而驳回输给并发的「通过」，就是钱退了东西照发。
  退款发起失败**不回滚驳回**，原因落在单上（`cash_refund_error`），后台按 `tradeOrderId` 到收付页重试。
- **快递单审核通过是「待发货」、没有取货码**；发货登记与现场核销共用 `donate:verify`（都是「把东西交出去」）；签收落「已领取（3）」，评价资格不用改。
  发货满 `auto-receive-days`（默认 15，清单⑱）未确认的系统自动确认。
- **付款人 openid 服务端现换**（`POST /v/donate/orders/{id}/pay` 只收 `wx.login` 的 code）：手机号登录的账号 openid 是合成的，不是微信的；也不信任客户端报上来的 openid。
- **没做的**：商城快递单的物流轨迹（Row 8 没有要求；要做时复用 `LogisticsClient` 查询 + 快照列即可）、快递费按地区 / 重量计价（计价器已留好入参）。

### 捐款批

众筹捐款、助学助困捐款接 trade；捐物走捐书批的物资流转；
**结对批预留的证书挂钩在此接上支付成功事件**。

**✅ 已落地（2026-09-17，V59 / V60 / V61 / V62）**——落地时才定的口径：

- **证书挂钩没有改到「钱到账」**：清单⑨的默认是「结对成立即出证」，结对批已经按它接好；
  再在到账时出一张就是同一条结对两张证书。协会答「钱到账才出证」时，把 `DonationCertificateListener`
  订阅的事件从 `PairEstablishedEvent` 换成到账（`DonationService.onPaid` 里结对那一支发），**证书的幂等键不用动**。
- **两本账分开**：结对项目的 `pledged_amount`（认捐，确认成立时累加）与新增的 `raised_amount`（到账）并存，
  结对登记新增 `paid_amount`；「已筹多少钱」自本批起展示到账额。众筹只有到账额。
- **结对捐款不收金额**：付的是「认捐额 − 已付」，付清之后不能再发起；一条结对至多一笔待支付
  （生成列唯一键 `uk_active_pair_payment`），否则两笔同时付成就超付。众筹捐款不设这条（每一笔是独立的心意，也不占资源）。
- **付过款的结对不能本人撤回**（与清单⑰同一个方向：退钱不交给志愿者的一个按钮），须协会取消、**取消提交之后**逐笔原路退款；
  有待支付的先关交易单，关不掉＝刚付款，整个撤回 / 取消放弃（「刚刚有一笔付款到账，请刷新后再操作」）。
- **退款先改账、后调渠道**：CAS 已到账 → 已退款并减回已筹 / 已付在同一事务，提交后才原路退款；
  原路退款失败**不回滚**，原因记在 `cash_refund_error`，到收付页重试（钱没退出去，但账上不能继续算它「已筹」）。
  **已登记开票的须先作废发票**（税务上的凭证，系统外处理）。
- **加锁顺序固定**：捐款 → 结对登记 → 项目。付款回写与协会取消都按这个顺序，反过来会互等成死锁。
- **公开捐赠记录只列已到账、姓名保留首字**（「捐*****」），金额与留言公开；手机号不出现。
- **众筹捐物**：项目上两个开关 `accept_money`（默认收）/ `accept_goods`（默认不收，存量项目行为不变），至少开一个；
  收物时收件人 / 电话 / 地址必填、不收物时不许填（填了又不收物，志愿者会以为可以寄）。收件信息是协会的、**明文公开下发**。
  捐物须已实名、项目在募集中且收物；运单 `biz_id` 就是项目 id（不像微心愿挂在认领上——众筹没有「认领」，谁都可以寄）。
  后台运单列表加 `bizType` / `bizId`，不传仍只看捐书活动。
- **⚠️ 压测撞出的连接池缺陷（影响商城快递批与本批）**：见 CLAUDE.md trade 行。修法是 trade 在事务**之外**发布
  `TradePaidEvent` / `TradeRefundedEvent`，订阅方加 `fallbackExecution = true`；`PaymentListenerConnectionTest`
  把连接池限成 1 条、单线程确定性复现（修之前两条都红）。两个证书监听器（活动 / 结对）仍是 AFTER_COMMIT + REQUIRES_NEW，
  它们挂在后台人工操作上、并发量到不了连接池大小，**没有改**——若日后挂到高并发入口上，照 trade 这次的改法做。
- **没做的**：「我的捐款」跨项目聚合（收尾批）；发票自动开具（清单⑦只预留）；众筹捐物的「本次活动数据」统计（捐书活动那套按活动截止时间算，众筹没有这个概念）。

## 六、跨批次承重条款

1. **积分模块不抽。** V2 说「待 V3 商城落地、积分来源真正多元时，再评估是否抽独立 `point` 模块」——
   **评估结论是不抽**：`honor → activity` 取 `PointService` 的先例已经跑通，donate 照做即可；
   抽模块是纯重构，要动三个模块的测试与 CLAUDE.md 的口径条款，而积分入账无论如何都在
   同一进程同一事务内，**抽出来没有功能收益**。V3 结束、消费方稳定后再复评。

2. **命名：权限点按模块，表名按聚合根概念。**
   权限点全用 `donate:` / `trade:`——现有 51 个点是 `activity:` / `honor:` / `org:` / `pub:` /
   `user:` / `data:`，**前缀 = 模块，无一例外**；权限码进库还要分配给账号，改名代价随时间涨。
   **表名的规则是「前缀 = 聚合根概念」**，多数情况下聚合根与模块同名（35 张业务表里 `activity_`9 /
   `volunteer_`8 / `honor_`8 / `publicity_`3 / `admin_`2，前三组恰与模块同名），
   而 `point_record`（在 activity）、`manager_application`（在 organization）、`squad_application`、
   `permission`、`organization_structure_node` 正是**概念与模块不重合时跟着概念走**的证据。
   据此**商城全 `mall_`、物资流转全 `donate_`**。
   ⚠️ 捐书条码库**不叫 `goods_barcode`**——在一个有 `mall_goods` 的库里会被当成商城的商品表，
   改 `donate_barcode_catalog`。
   **这条日后要被引用来裁决新表名，理由必须写准。**

3. **爱心企业边界。** Row 8「商品赞助单位需要入驻爱心企业」，但 enterprise 不在 V3 ⇒
   商品留 `sponsor_enterprise_id`（可空）+ **赞助方名称快照**，**后台代发布**——
   Row 15 F 原文就写着「后台可以以企业的名义代替企业发布积分商品」，**有出处，不是绕路**。
   企业主页、企业自助登录发商品、积分流转、企业设核销员留 V4。
   **这条写在最前面**，否则做到一半会发现在等 enterprise。

4. **迁移纪律**（继承 V2 逐条踩出来的）：一个迁移文件只放**一条**有失败可能的语句；
   文件里**不得出现美元花括号占位符**（注释里也不行，Flyway 不区分注释）；
   最低 **MySQL 8.0.17**，由 `DatabaseVersionGuard` 在 Flyway **之前**校验；
   迁移只要可能在任何环境跑过就**不能原地改**；**版本号按开工顺序领**。
   ⚠️ **挑号要跨分支查，`ls` 只看得见当前分支**——商城批就栽在这上面：在 v2-batch5 上 `ls` 看到 V40 是空的，而 v3-planning 早已占了它，结果两个迁移顺延为 V41/V42。命令见 CLAUDE.md 迁移纪律。
   **顺延只在「从未在真实环境执行过」时才安全**——那条规矩保护的是已部署的迁移；跑过一次之后就只能往后加新号。

5. **锁与测试纪律。** Testcontainers（MySQL + Redis）；并发用例一律 `Future.get()` 收结果；
   要覆盖「事务内撞唯一键」必须构造**真并发时序** + 显式 `ISOLATION_REPEATABLE_READ` +
   断言快照读不到对方；关键行为做**变异验证**。
   **选锁一律按「读完之后改不改这一行」判据**（D7(b)），**不照抄别处的锁类型**。
   ⚠️ D7 的两条要配 `MedalReviewIsolationTest` 那种隔离用例——顺序调用的用例在它们上面永远绿；
   **库存那条还要一条双写并发用例，能在改回「先 S 后 X」时红**。

6. **通知只走 `SmsNotifyService` / `NotificationService`。** 新场景先在 `SmsNotifyTemplate` 登记
   （模板键 + 变量名 + **顺序** + javadoc 写清落点），业务侧 `TPL.params(...)` 按序传；
   收件人口径继续由 auth 的 `listNotifiablePhones` **一处说了算**。
   微信那半若仍未定（V2 问题一），一律只发短信 + 站内提示，**写入点不变、调用方不改**。

7. **一句风险陈述**（据实记一次，不重复）：V3 结束时后端将再多约 60 个端点、10+ 权限点
   **没有任何界面能到达**，V2 已有的这笔欠账会继续放大；捐书批更甚——扫码动作连手工验证路径都没有，
   故其完成定义里加了测试脚本。**这是既定交付形态选择的结果，不是本规划要解决的问题。**

## 八、待协会决策（16 条）

完整版见 [`协会待确认清单-v3.md`](协会待确认清单-v3.md)。⚠️ **每一条的「阻塞与否」都按重排后的批次
重新推过，不是沿用早期版本的注记**——批次一动，同一个问题的紧迫度就变了。最典型的是 **⑧**：
早期版本里它在 trade 之后，重排后变成**捐书批的直接前置**。

**重排的收益要说准**：捐书批摆脱的是**备案**（周级、不可控），**没有摆脱快递100 账号**（天级、可控）。
不写这个量级差，读的人会以为它零外部依赖。
