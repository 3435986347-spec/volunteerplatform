## 三、核心设计判断 D1–D12

### D1　社区的门分四层，**缺一层就是一个洞**

Row 23 D 列两句话 + Row 73 + Row 23 F，合起来是四道互相独立的门：

| 层 | 挡什么 | 落点 |
|---|---|---|
| ① 登录态 | 一切 `/v/social/**` | 路由过滤器（已有） |
| ② **已验手机号** | **看帖**（「登录验证手机号才能看帖子」） | 复用 V3 微心愿批的判定——**微信登录的账号可能根本没绑手机号**，登录态挡不住 |
| ③ 已实名 | 发帖 / 评论 / 点赞（「未实名的不能发帖、评论、点赞」） | service 入口 |
| ④ 处置 | 发帖 / 评论（Row 73「限制其使用」+ `SanctionScope.COMMUNITY`）；**禁言**（Row 23 F「禁止发帖几天、禁止评论几天、禁止点赞几天」） | `SanctionQueryService`，**当前读 + 父行锁**，与活动报名闸门同形 |

⚠️ **④ 的两处都必须挂闸门、且必须在事务里取当前读**——V2 第 5 批记过的两课（「只加父行锁是不够的」「autocommit 下 FOR SHARE 随语句释放」）在这里同样成立。
⚠️ **「禁止点赞几天」比 `COMMUNITY` 更细**：默认**扩展 `SanctionScope`**（新增 发帖 / 评论 / 点赞 三个细粒度域，`COMMUNITY` 蕴含三者、`ALL` 蕴含一切），
**不另建第二套限制表**——两套「他能不能发帖」的事实来源，正是本项目反复栽的那类跟头。
禁言的**开单入口**另议（Q2）：它是社区审核员的日常动作，走奖惩两级审核太重。

### D2　问卷引擎落 `organization`，**不新建模块、不放 common**

五处消费方：投诉建议（data）、报名管理团队 / 评优评先（organization）、意见反馈（user）、考试（organization，D3）。

| 选项 | 结论 |
|---|---|
| 放 `common` | ❌ common **零 Mapper、零 `@TableName`**（V3 D3 同一条边界） |
| 新建 `form` 模块 | ❌ 多一个模块要改父 POM、api pom、Reactor 行数，却买不到隔离——消费方都在同一进程同一事务 |
| **放 `organization`** | ✅ `data` 与 `user` **本来就依赖 organization**（看板取分队数、志愿者管理取小组名），不产生新方向、不成环；Row 44/46/47 本就在组织域 |

**表名前缀 `org_form_`**（承重条款 2：前缀 = 聚合根概念）。

### D3　考试与问卷**共用题型、不共用聚合**

题型集合相同（单选 / 多选 / 判断 / 填空 / 简答 / 文件 / 日期），但语义根本不同：
问卷**没有对错**，考试**有标准答案、有分值、有及格线、有人工阅卷**。硬塞进一张表会让每条问卷查询都带着
一堆永远为空的评分列，而每条考试查询都要排除问卷行——**两者只共用题型枚举与答案格式校验**
（`organization.form.support.QuestionType` + 一个无状态校验器），各自建表。

### D4　「活动临时负责人」是一张**资格表**，不是 `volunteer` 上的一个标记

需求要的是**历史**：「有历史考试板块」（Row 45）、「评价过低……取消资格，也可以直接取消」（Row 14）。
一个布尔列回答不了「他什么时候拿到、为什么被取消、取消后能不能再考」。
故 `org_temp_leader_qualification`（授予来源 = 某次考试 / 撤销人 / 撤销原因 / 生效与撤销时间），
**「当前是否临时负责人」按时间与状态现算**（同处置「到期靠比时间不靠 cron 改状态位」）。
消费方三处：`enroll_open_leader` 报名窗口（V8）、「我的·所属职务」（Row 24）、名单公示「优先展示」（Row 13 F），
**一律经 organization 的只读服务**，activity 不直连资格表。

### D5　爱心企业是**第三类主体**，要第三套登录态

企业账号既不是 `volunteer` 也不是 `admin_user`：它有信用代码、要注册审核、能发帖（主页是企业主页）、
能发积分商品、不能参加志愿活动（Row 5 G）。故：

- `enterprise_account` 独立表 + **第三套 `StpLogic`（type=enterprise）** + `/e/**` 路由段；
  与志愿者 / 管理端 token 互不通用（沿用 `StpAdminUtil` 与志愿者端隔离的形状）；
- **企业核销员仍是志愿者**（Row 8 F「企业可以设置某一个志愿者为企业核销员」）——
  V3 卷批的 `mall_verifier` 已预留企业作用域列，V4 只是把「谁能指派」从后台放开给企业；
- **企业积分流转**（Row 15 F「企业将存下这个积分，后续用于兑换企业权益」）＝**独立账本**
  `enterprise_point_record`，**不写 `point_record`**：后者是志愿者积分的唯一事实来源，
  混进企业流水会让排行榜、积分中心的每一条 `SUM` 都得记得排除企业行。
  入账挂在**核销那一刻**（东西真的发出去了），幂等键 `uk_source(source_type, source_id=订单 id)`，同账本纪律。

### D6　「最热 = 当前一个小时综合」要**按小时分桶**，且热度丢了可以重算

热度只是排序依据、不是账：Redis 被清一次，最坏是「最热」页签短暂退化成按时间排——**可接受**，
与「提醒标记必须落库（Redis 被清会让全部历史场次重新群发）」性质相反。
故热度计数放 Redis 小时桶（阅读 / 点赞 / 评论加权），**累计数据**（帖子数据 Row 23「查看量、点赞量、评论量、分享量」）落库。

### D7　审核是「先发后审」，**关键词命中是「先藏后审」**（默认，Q1）

Row 23 F 原文：「用户发布帖子后正常显示，但后台显示为待审核阶段」——先发后审；
「如触发关键词，则自动进入后台插队审核」——只说了插队，没说藏不藏。
**默认命中即对他人隐藏、本人可见**：这是一个有大量未成年人的平台，一条命中关键词的帖子在审核员看到之前
公开挂着，代价远大于「晚几分钟显示」。「审核几次」默认**串行 N 级**（N 可配 1–3，Q3）。

### D8　私信先落库、后推送；**聊天记录的查看权是一个权限点**

「所有聊天记录均保存在系统后台、查看权限仅为最高管理员，亦可由管理员下放」（Row 23 F）——
这正是 `honor:sanction-all` 那种「默认只有超管、可显式下放」的形状：**权限点 `social:chat-view` 默认不授任何人**。
推送走 WebSocket（握手用 Sa-Token 校验），**消息先落库再推**——推送失败只是「晚看到」，落库失败才是丢消息；
离线拉取走普通 HTTP。部署侧要给 nginx 加 `Upgrade` 头（承重条款 7）。

### D9　操作日志：**只追加、异步、绝不影响业务**，查看权默认只有超管

Row 62「所有操作都要记录……避免出现信息泄露追责难题」。落地为：
`/a/**` 全部写操作 + **敏感读**（导出、看明文手机号 / 身份证、看聊天记录、看到家详细地址）由拦截器记录；
「谁点击了哪个页面」由前端上报端点补齐（后端看不见纯前端路由切换）。
写入**异步批量**，失败只记 ERROR——与「通知失败绝不影响业务」同一条取舍。
**日志表不提供删除入口**；保留期由定时任务按时间清理（Q8）。

### D10　活动相册的「上传给积分」是新积分来源，**非消费类、要审核**

Row 11「上传多少张照片给多少积分（需要审核才发放）」。按积分纪律：
**新来源必须分配新码**（`PointSourceType.ALBUM = 7`，非消费类，计入累计获得与排行榜），
`source_id` = 上传批次审核单 id，`uk_source` 保幂等；审核通过才入账（与奖惩「审核通过才入账」同形，
与商城「下单即扣」相反——那里是用户主动消费、要占位，这里是奖励、未审不该生效）。

### D11　志愿者证的扫码页是**公开的**，所以链接里不能是裸 id

「其他人扫码的话能看得到他的志愿者信息」——扫码的人不一定是本平台用户，页面必须免登录。
**二维码里放签名令牌、不放 `volunteer.id`**（裸 id 可枚举，等于把全体志愿者名册公开）；
公开字段默认只含头像 / 姓名（打 *）/ 编号 / 注册时间 / 累计时长 / 活动次数（Q5）。

### 问卷引擎批 · 落地时定下的口径

- **发布后题目冻结**（写在 UPDATE 的 WHERE 里，与发布同一行互斥）：有人按这套题作答之后再改题，旧答卷的含义跟着变（选项 B 从「是」改成「否」，历史答卷就说反了）；
  要改就复制出一份新草稿。答卷因此只存「题目 id + 规范化的值」，不快照题面。
- **一个场景同时至多一份收集中的问卷**（通用问卷除外），生成列唯一键 `uk_active_scene` 兜底：报名管理团队页面只认「当前问卷」，两份同时收集会让志愿者看到哪份取决于排序。
- **「每人一次」靠生成列唯一键 `uk_active_single`**，不靠先查再插；值快照在答卷上（发布后改不了这个设置，快照只为唯一键不必连表）。
  ⚠️ **报名管理团队的问卷不能设「每人一次」**——被驳回后要能再申请，第二份答卷会撞在唯一键上；次数由申请流程控制。
- **提交与停止收集串行**：提交的第一条语句是锁住问卷行的当前读（`FOR SHARE`，读完不改这一行），停止是对同一行的 UPDATE。
  普通快照读的提交不会被正在进行的停止挡住，会读到「收集中」并交成功——`FormSubmitConcurrencyTest` 用裸 JDBC 事务先把停止写进去不提交，确定性地钉住这件事。
- **文件题只收本系统传到 `form/` 下的附件**（common 新增 `FileStorageService.isOwnUpload`：前缀 + 本项目生成的对象名形状 `yyyyMMdd/32 位十六进制[.扩展名]`，`../`、别的目录、外链一概不认）：
  不校验的话答卷里可以塞任意外链，管理员在后台点开的就是别人的页面。OSS 未启用时的占位 URL 同样认得出，本地联调走得通。
- **报名管理团队不推翻 V23**：固定三项照旧必填；场景 2 有收集中的问卷时答卷必填、与申请同一事务；没有问卷时照旧只交固定三项；
  问卷已停止而请求带着答案时**报错而不是默默丢掉**（他照着一份已停止的问卷填完了，丢掉他的答案他也不知道）。资格校验（已有待审 / 已是管理团队）排在交答卷之前，被拒的申请不留答卷。
- **批量下载把答卷合成一列**（「1. 题目：答案」逐行）：不同时期的申请可能答的是不同的问卷，按某一份问卷的题目拆列会让其余的对不上。
- **志愿者能直接填的只有通用与评优评先两个场景**：报名管理团队的答卷单独交会留下没有申请的孤儿答卷；意见反馈 / 投诉建议要等各自的批次接上处理流程——现在放开，收上来的东西没有人处理。
- **两个权限点分开**：`org:form-data`（看答卷与导出）与 `org:form`（管问卷）分开授权，答卷里有填写人的手机号；读问卷列表 / 详情两者任一即可。
- **没做的**：评优评先的评选流程（Row 47 只写「需预留」）；答卷的删除 / 作废（需求没有提，答卷是填写人的原始意思表示）；按答案筛选答卷。

- **工单在谁手上谁看**：`data:complaint` 只看得到、只动得了当前在本部门的工单，转走就看不到；`data:complaint-all` 看全部、可代任何部门处理（Q16）。
  范围在控制器按登录态算好（账号 → 部门、`hasPermission` → 全部门）传给服务层，服务层不碰 Sa-Token；没填部门的账号一条都看不到。
- **状态迁移全是 CAS、条件里带「读到时的部门」**：受理 / 流转 / 答复并发时只有一个成功（`ComplaintConcurrencyTest` 30 轮偏置起跑，两种结局都出现过）。
  **输家的报错在事务结束之后重新读一次**再说「刚被处理成了什么、在哪个部门」——用读到的旧对象拼、或在同一事务里普通读复核，都会说成旧状态
  （用裸 JDBC 事务持住行锁确定性地构造，V3 反复撞过的那条）。
  ⚠️ **变异验证撞出一处用例缺口**：去掉 CAS 里的部门条件，30 轮赛跑用例照样全绿（预检读与 CAS 之间只有几微秒，调度撞不到），
  补了「答复撞上正在进行的流转」的确定性用例才红——赛跑用例证明「两种结局都出现过」，证明不了窄窗口里的条件是承重的。
- **志愿者看到的处理进度**：提交 / 受理 / 流转 / 答复四步，**流转理由与内部备注不下发**（那是部门之间的话）；后台看全部并带操作人。
- **答复即办结**，站内提示与工单同一事务；短信 `COMPLAINT_REPLIED` 由 `SmsNotifyService` 等提交后发，**答复只放开头**（默认 30 字，Q19），全文在工单详情。
- **所有登录账号都能提**（游客也能，Q17），禁用 / 注销不能；**24 小时条数上限**（默认 5，按人加锁再数，连点越不过上限）；图片只收本系统上传的（与问卷文件题同一判定）。
- **类似于问卷收集**：协会为场景 5 发布了问卷时答卷必填，与工单同一事务（接问卷引擎批的 `submitForScene`）；没有问卷时只交类型 + 内容。
- **补 V3 的遗漏**：`POINTS_ORDER_REVIEW`（卷批接上的商城审核结果短信）当时漏进了 `SmsNotifyService.WIRED` 启动自检、api 的 yaml 与 `部署/api.env.example`——
  部署时没人知道要配、配漏了启动也不报警。这次与 `COMPLAINT_REPLIED` 一起补齐（13 条已接）。
- **没做的**：工单评价 / 满意度回访（需求没有）；超时未受理的催办（需求没有「时限」）；志愿者补充材料 / 追问（需求没有，要做就是在进度表加一种动作）。

- **没做的**：地址与商城收件信息打通；站内提示的「免打扰」；年级提示的站内提示 / 短信（资料里的标记由前端弹窗，没有额外推送）。

### 组织架构维护批 · 落地时定下的口径

- **节点沿用 V5 的表，人另起一张 `organization_structure_member`**（V69）：节点就是部门（V5 种子里的「组织部」「秘书部」就是这么用的），
  放人时写职位。**一个人在架构里至多一个位置**（生成列唯一键 `uk_active_volunteer`，移出即释放）——「显示他是哪个部门的什么职位」是单数，
  名字下面也只放得下一行（Q23）。已在架构里的人再放一次报「请用修改把他挪过去」，不静默替换。
- **所有写操作一把全局锁串行**（`lock:org-structure`，锁在事务外）：挪节点要查「会不会成环」、删节点要查「还有没有子节点和人」、放人要查「节点还在不在」，
  都是先查再动；两个人同时把 A 挪到 B 下、把 B 挪到 A 下就是一个环。架构一天也就改几次，串行的代价可以忽略，逐个配行锁反而容易漏一处。
  ⚠️ **这把锁靠赛跑证明不了**（窗口只有几毫秒）——`StructureConcurrencyTest` 第一条由测试线程直接持锁、断言六个写操作都在等它。
- **删除不连带**：下面还有节点或人的节点拒绝删除，先挪走——连带删掉会让人莫名其妙地从架构里消失。
- **名字下面那一行现算**：`StructureService.positionLabelsOf` 返回「部门 · 职位」，「我的资料」、志愿者管理列表与详情三处用它；
  V1 在 `volunteer.position` 上留的那一列（「后台设置，前端名字下展示」，一直没有写入口）**不再读写**——两处都能改「职位」迟早各说各的。
  改部门名、挪部门、改职位、移出都即时生效，没有快照。
- **电话**：Row 6 原文「展示名字、部门、职位、电话」，进了架构的是协会的部门成员，电话全显示（Q24）；
  但**查看者是游客（未实名）时不下发**——游客收个验证码就能登录，给游客下发等于把部门成员的电话公开在网上。后台恒下发。
- **权限**：一个权限点 `org:structure` 管全部写操作（Row 6「均有最高权限操作」），默认只有超管有（超管 `*` 通配）；读树的志愿者端接口仍只需登录。
- **没做的**：一个人兼任多个部门（Q23）；节点排序的拖拽批量接口（逐个 `PUT` 改 `sort`）；架构变更历史（需求没有）。

- **公示窗口按时间现算，不靠定时任务撤**：组织部「确认名单」写 `roster_publish_time`；「活动开始」＝`start_time` 已过**或**负责人已点开始（`run_status≠0`），

### 社区核心批 · 落地时定下的口径

- **新模块 `hengde-volunteer-social`**（依赖 common / auth / honor——主页勋章；排在 honor 之后、api 之前，Reactor 13 行）。
- **可见性只写在一段 SQL 里**（`SocialPostMapper.VISIBLE`）：帖子流、搜索、TA的主页、详情、点赞 / 评论 / 分享的前置判断、主页发帖量都拼它。
  规则：官方帖所有人可见；自己全可见；别人的帖——被「不让TA看」的一律不可见，其余按 0 不限制 / 1 隐藏 / 2 **作者关注的人**可看 / 3 **关注作者的人**可看（Q27）。
- **四层门**（D1）：看（帖子流、详情、评论、主页）要**已验手机号**；发帖 / 修改 / 评论 / 点赞 / 关注 / 设置 / 不让TA看 / 上传要**已实名**；
  发帖（含修改）/ 评论 / 点赞各挂一个处置能力域，闸门在写入事务里取当前读 + 父行锁（与活动报名同形，`SocialConcurrencyTest` 用裸 JDBC 事务锁住志愿者行、插一条处置不提交，确定性地钉住「发帖等它并看到它」）。
  **蕴含关系只写在 `SanctionScope.implying` 一处**，闸门的快照读与当前读两份查询都从这里取集合。**取消点赞 / 取关 / 删自己的内容不挂闸门**。
- **计数**：点赞与关注靠唯一键防重、按影响行数 ±1；评论删除是 CAS，同时删同一条只减一次。主页的发帖量 / 粉丝量 / 关注量现算；**发帖量只数看的人看得到的**（否则隐藏帖从数字上露出来）。
  查看量按打开次数计。⚠️ **同一个人的点赞 / 关注 / 不让TA看按人上锁**（`lock:social:volunteer:`）——并发用例撞出来的：同一个人连点「赞 / 取消」会让两个等在被删行上的 INSERT 同时拿到 S 锁、再互等插入意向锁而死锁，唯一键防得住重复、防不住这个。
- **最热**（D6）：Redis 小时桶 `social:hot:yyyyMMddHH`，查看 1 / 点赞 3 / 评论 5 / 分享 4（可配），本小时 + 上一小时 ×（本小时剩余比例）；取消点赞不扣。Redis 出任何问题只打 WARN、「最热」退回按时间排，不让一次点赞因 Redis 失败。
- **先发后审**（D7）：发帖 / 修改落 `review_status=待审核`，本批不据此隐藏；关键词「先藏后审」、审核员、举报、禁言入口、置顶、互动通知聚合都在治理批。
- **官方帖**：部门取后台账号的 `department` 快照在帖子上；删帖 / 删官方帖下评论限本部门，持 `social:official-all`（默认给宣传部，Row 23「宣传部可以删除其他部门发的帖子」）不限；官方身份的评论只能落在官方帖下。
- **不露实名**：社区出参只有昵称 + 头像（没设昵称显示「志愿者」+ 编号尾号），真实姓名与学校的后台界面属治理批（Row 23 F「最高权限管理员才可以看到」）。
- **视频直传**（Q11）：`FileStorageService.presignPut` 按扩展名白名单（mp4 / mov）与声明大小（≤100MB）签一条限时 PUT，Content-Type / 公共读 ACL 头参与签名（火山 TOS 连 Content-Length 一起签，阿里云 V1 签名不含大小）；发帖时再核对 URL 在 `social-video/` 下。
  ⚠️ 与支付、快递100 一样，**真实对象存储上的直传没有端到端验证过**，用例只跑到存储未启用时的占位地址。
- **没做的**：@TA（需要对方关注）与互动信息（治理批的互动通知）；帖子举报；下载（前端动作）；主页二维码（前端生成）；视频时长 5 分钟上限（服务端拿不到时长，前端约束）。

### 社区治理批 · 落地时定下的口径

- **可见性的新条件仍只写在 `SocialPostMapper.VISIBLE`**：别人看不到后台隐藏的、驳回的、命中关键词还没审完的；作者自己始终看得到（出参告诉他是哪种状态）。
  没命中关键词的帖子先发后审照常显示（D7）；官方帖不进审核。
- **审核**（Q3）：`social_review_setting` 单行存级数（1~3），`social_reviewer` 按级指定审核员（超管不必指定）。第 k 级只有第 k 级审核员能审；**同一个人不能审同一条帖子的两级**；
  通过是一条 CAS（带「还停在上一级」），两个人同时点只成一个；任一级都可驳回，驳回同一事务写站内提示（类型 7）。调低级数时已经过够新级数的待审帖直接算通过，否则它们再也等不来「下一级」。
  改帖重回第 0 级、重新判关键词。审核队列：命中关键词的插队在前，其余先发先审。
- **关键词**（Q1）：正文不区分大小写地包含即命中，每次发帖 / 改帖现查全表（刚加的词下一条帖子就生效）；命中词记在帖子上给审核员看。私聊的关键词在私信批。
- **举报**：生成列唯一键保证同一个人对同一对象只有一条待处理；**处理按对象结案**（一条 UPDATE 结掉这个对象上全部待处理的），所以「成立」与「不成立」并发只成一个；成立可顺带隐藏（仅帖子）或删除，与结案同一事务。
- **禁言**（Q2）：`social:ban` 即时生效、不走奖惩两级审核，只能开社区能力域（2 / 4 / 5 / 6）且必须给天数；**限制本身只写 `volunteer_sanction`**（来源类型 2、source_id＝`social_ban.id`），
  闸门不认第二张表；`social_ban` 只是开单与解除的留痕，本人在奖惩中心的处置查看里看得到。「封号」仍走账号禁用 / 奖惩「拒绝使用本程序」。
- **互动**：与点赞 / 评论 / 关注同一事务写入；自己对自己不记；点赞与关注按「收件人 + 类型 + 谁 + 哪条帖子」生成列去重（反复点只记一条）；回复别人的评论时被回复人收到「回复」、帖子作者另收「评论」（同一个人只收一条）。
  **汇总提示**（Row 23 D）：每人一条水位，CAS 推进成功才写站内提示（类型 6），同一段互动只提示一次；整个任务一把全局锁（`lock:social:interaction-digest`），多实例 / 重叠触发只跑一个。
  原文是「订阅消息」——报备模板之前只落站内（Q13）。
- **真实姓名与学校**：后台两个列表只在持 `social:real-name`（默认不授任何人、超管通配）时下发（Row 23 F「最高权限管理员」）。
- **没做的**：@TA（「需要对方关注」）；评论的关键词风控（原文只说帖子与私聊）；举报人收到处理结果的提示（需求没有）；审核超时提醒。

### 活动相册批 · 落地时定下的口径

- **自动建册＝第一次打开或上传时建**（get-or-create），不挂在发布活动的事务上——存量活动一样有相册，发布路径不必改；生成列唯一键 `uk_active_activity` 保证一个活动一个，并发建撞键读回赢家。
  只给已发布 / 已结束的活动建；删掉的相册释放唯一键，再打开建一个新的空相册（照片不迁移）。后台可新增不挂活动的相册（F 列）。
- **权限**（Row 11 D）：看 / 单张下载——全体**已实名**志愿者；往这个活动的相册传——**报名已通过**的志愿者与**本活动志愿者负责人**（待审核的报名不算）；往任何相册传——**管理团队**（`isActiveManager`）；
  删相册 / 删照片 / 批量下载 / 管理 / 积分审核——后台各一个权限点（部门到人的映射由超管授权表达，与奖惩批同理）。
- **积分**（D10 / Q10）：每一批上传是一张审核单，**审核通过那一刻**按「这一批现在还没删的照片数」算分（先删掉凑数的照片再审，就按删后的算），规则默认每 3 张 1 分、**同一个人在同一相册累计不超过 10 分**，0 分不入账。
  上限复核在当前读锁住「这个人在这个相册的全部批次行」之后做（`sumAwardedForUpdate`，走 `idx_album_uploader`）——两批同时审核会各自以为还差几分而越过上限；`AlbumConcurrencyTest` 用裸 JDBC 事务先锁住那些行、确定性地钉住审核在等它。
  规则改动只影响之后审核的批次；规则关着时新上传的批次直接「不参与积分」。流水 `source_id`＝批次 id。
- **同步交流平台**（Row 30）：上传事务提交后发 `AlbumPhotosUploadedEvent`，social 的 `AlbumSocialSyncListener` 以本人名义发帖（「【相册标题】评论」+ 前 9 张相册原图），**照常过已实名、禁止发帖闸门与关键词风控**；
  被禁言 / 没实名等业务拒绝记 WARN、其余记 ERROR，都不外抛、不补偿（V4规划 七）；成功后回写批次上的 `social_post_id`。依赖方向 social → activity。
- **没做的**：后台服务端打包 zip（批量下载只给地址清单）；照片评论（Row 11 未要求；Row 30 的「评论」随批次一起提交）；相册封面自选（取最新一张）；删相册时迁移照片。

### 临时负责人考试批 · 落地时定下的口径

- **落 organization、包 `com.hengde.organization.exam`，表前缀 `org_exam_`**（D2 / D3）：题型编号、选项编号分配、答案格式与规范化**全部复用 `FormAnswerValidator`**，考试只加两件事——标准答案与分值（`ExamScoring`）。
  考试只用前五种题型（文件 / 日期题拒收）；**每道题都是选答**，没答按 0 分，不会因漏答交不上去。标准答案用作答同一套规范化（多选按选项顺序排好），判分直接比相等。
- **判分**：单选 / 判断全对得满分；**多选全对才得分、不给部分分**（Q33）；填空 / 简答一律人工阅卷，参考答案只给阅卷人看。
  没有主观题的试卷交卷即出分；有的落「待阅卷」，**一个人同时至多一份**（生成列唯一键 `uk_active_pending`）。总分达到及格线即授予资格，与出分同一事务。
- **试卷**：草稿 → 开放中 → 已停止；题目 / 分值 / 及格线 / 有效期**只在草稿时能改**（条件在 UPDATE 的 WHERE 里），开放过的要改走复制；**同一时刻至多一份开放中的试卷**（`uk_active_open`）。
  交卷事务第一条语句是试卷行的当前读共享锁，与「停止」串行（`ExamConcurrencyTest` 用裸 JDBC 事务先写停止不提交，确定性地钉住）。
- **资格**（D4）：`org_temp_leader_qualification` 一张表，**有效与否按时间现算**（没撤销且不设期限或还没到期），不靠定时任务；有效期从出分时刻起算，试卷上配置（Q6，不填＝长期有效）。
  一个人至多一条没撤销的行（`uk_active_qualification`）；到期的行不改状态、会一直占着唯一键，所以**授予新资格前先把这个人到期的行以「资格到期」收尾**。
  ⚠️ **收尾按主键做，不按 `volunteer_id` 范围 UPDATE**：对还没有资格行的人做范围 UPDATE 会在 `idx_volunteer` 上留间隙锁，两个 id 相邻的人同时及格就互等插入意向锁——压测三次三中 `Deadlock found`，与结对批登记同形；
  要收尾的行先普通读找出来，这个人的写入已由按人的锁串行。
- **撤销**（Row 14 / Q6）：组织部手动撤销、必须写原因，只能撤有效的；「评价过低」**不自动判定**。撤销或到期之后可以再考。
- **串行化**：交卷、阅卷、撤销持同一把按人的 Redisson 锁 `lock:temp-leader:volunteer:`（锁在事务外）——交卷前「已经是临时负责人吗 / 有没有待阅卷的」两条判断与阅卷授予资格之间就没有窗口。
  阅卷 CAS 里的「还在待阅卷」在这把锁之下是第二道防线：单独去掉它用例照样绿，锁与 CAS 同时去掉并发阅卷才出分多次（变异验证记录）。
- **志愿者看不到标准答案与逐题得分**（Q34）：历史里只有自己的作答与总分；重考次数不限、没有冷却期。
- **消费方**：① 报名开放时间——V8 的 `enroll_open_manager` / `enroll_open_leader` 此前从没生效过；现在管理团队（`manager_flag=1`）与临时负责人若活动另设了自己那一档且早于志愿者时间，按更早的算，
  **留空＝没有提前**（Q35；按「留空即时可报」解读，存量活动上线那一刻这两类人就能报所有还没开放的活动）；代报名按被代的每个人各自的身份算、有一个没到就整批不报。
  ② 名单公示与后台按活动的报名列表：管理团队在前、临时负责人其次（Row 13 F「优先展示管理团队和考试通过活动临时负责人的志愿者」）；后台列表的排序只在一页之内（身份在别的域，跨页排序要拼外域表）。
  ③ 「我的」所属职务（Row 24）。
- **没做的**：考试通知短信（Q13，报备前只有页面状态）；按题库随机组卷 / 限时 / 防切屏（需求没有）；「评价过低」自动预警；负责人管理单次活动的额外权限（「活动负责人」仍由组织部逐场指派，临时负责人身份只影响报名时间与排序）。

### 志愿者证批 · 落地时定下的口径

- **一人一张、第一次打开时发**（get-or-create，`uk_volunteer` 撞键读回赢家）；只存扫码令牌，**证件上的信息一律现算**（时长 / 次数与排行榜、勋章进度同一口径 `ActivityRankingQueryService`，所属职务取临时负责人资格）。游客没有证，停用 / 注销的证核验即失效。
- **令牌**（D11）：24 字节随机数的 base64url＝32 个字符（小程序码 scene 的上限）；`token` 列 `ascii_bin`——base64url 区分大小写，默认排序规则会把大小写不同的两个令牌当成同一个（V34 那一课）。**本人可重置**，旧码当场失效。
  核验端点只收令牌、形状不对直接拒；未知 / 旧令牌 / 持证人失效**一律同一句话**，不给探测的余地。
- **公开字段**只取 Q5 默认（头像、姓名只留姓、编号、注册时间、累计时长、活动次数），`VolunteerCardServiceTest` 用反射钉住出参字段集合——将来往里加手机号、学校、完整姓名会当场红。
- **码图**：配了 `WX_APPID` / `WX_SECRET` 时 `wxacode.getUnlimited`（auth 新增 `MiniappCodeService`，失败返回 null 不抛），scene＝令牌、按令牌缓存在 Redis（令牌不变图就不变）；
  生成不了时回退普通二维码，内容为 H5 核验地址 `?token=`，没配地址时为 `hengde-volunteer-card:令牌`（只有本小程序的扫一扫认得）。⚠️ **没有真实 AppID，小程序码那一段只用替身验证过本系统怎么用它**。
- **没做的**：证件的图片渲染（「类似身份证」的版式由前端画，后端给字段与码图）；后台代重置 / 吊销（本人重置 + 账号停用已覆盖）；核验记录（谁扫过我的证，需求没有）。

### 爱心企业批·账号段 · 落地时定下的口径

- **新模块 `hengde-volunteer-enterprise`**（依赖 common / auth / donate；排在 social 之后、api 之前，Reactor 14 行）。**第三套登录态** `StpEnterpriseUtil`（type=enterprise，放 auth 与 `StpAdminUtil` 并列），api 启动时显式 `SaManager.putStpLogic`（管理端那一课）。
- **状态**：0 待审核 / 1 正常 / 2 驳回 / 3 暂停。**待审核与驳回能登录**、只能用认证 / 我的企业 / 上传头像（看状态、补资料、重新提交）；暂停登录不了。
  **api 的 `EnterpriseAccountGate` 每个 `/e/**` 请求按当前状态放行**——暂停 / 删除当场踢出（旧 token 的下一次请求就 403），放行清单是显式的，新加的企业端接口默认要审核通过。
- **注册**（Row 15）：负责人手机验证码（新场景 `enterprise-register`），**格式与唯一性先查完、最后才核验证码**（核验成功即作废，填错信用代码不该让人重收短信）；信用代码按 GB 32100 校验位校验（Q4：不调第三方核验）；
  登录账号与信用代码在未删除的账号里唯一（生成列唯一键，删除即释放；账号不区分大小写，先查只为友好提示、并发注册靠唯一键）。负责人手机号密文 + 哈希；对外电话是企业主动公开的明文。头像只收本系统传到 `enterprise/` 下的（企业端 `POST /e/files/image`，**注册接口不收文件、不开匿名上传**）。
- **资料**：头像 / 介绍 / 地址 / 对外电话随时可改；**企业名称 / 信用代码 / 项目负责人只在待审核或驳回时可改**（写在 UPDATE 的 WHERE 里——`EnterpriseConcurrencyTest` 用裸 JDBC 事务把状态改成正常不提交，确定性地钉住改名要等它并被拒），审核通过后改名等于绕过入驻审核。
- **后台**：3 个权限点（`enterprise:manage` / `enterprise:audit` / `enterprise:export`，导出含负责人手机号单拆；共 89）。状态迁移全是 CAS，输家报「当前：xx」；暂停 / 删除立刻 `StpEnterpriseUtil.logout(id)`；后台注册直接为正常、审核人记本人。
- **志愿者端**只列正常的企业，出参没有信用代码、负责人与登录账号（反射用例钉住字段集合）。
- ⚠️ **两个测试侧的坑**：① Sa-Token 1.43 的请求上下文按线程绑定，服务层用例里成功登录要 `SaTokenContextMockUtil.setMockContext()`（`RequestContextHolder` 挂模拟请求没用）；② 迁移第一版给登录账号与信用代码用了 `ascii` 字符集，后台搜索的 `LIKE` 报 `Illegal mix of collations`，改回默认 utf8mb4（V77 从未在任何环境执行过，原地改）。
- **没做的**（本段）：审核结果通知（Q13，模板报备前只在企业端资料页看状态）；负责人换手机号（请平台改）；企业账号的「切换身份」联动（三套 token 各自登录）。

### 爱心企业批·商品段 · 落地时定下的口径

- **商品还是 V3 商城那一套**（`mall_goods` 的 `sponsor_enterprise_id` 从这一批起有值）：企业端 `/e/donate/goods` 只是多了「只能管自己的」入口——修改 / 提交 / 删除 / 隐藏的「本企业」条件都写在 UPDATE 的 WHERE 里；**改已上架的退回待审核、审核中不许改**沿用商城批；审核仍在后台。
  赞助方名称取企业名称快照；企业不能设「必须持卷」（卷是平台发的）；后台代发布（Row 15 F）要求企业正常，走同一个 `createForSponsor`。
- **企业暂停 / 删除 ⇒ 赞助商品不可见、不可兑换**（V78 `mall_goods.sponsor_suspended`，由 enterprise 在暂停 / 恢复 / 删除企业的**同一事务**里整批置位）：志愿者端列表与详情过滤；**承重的是扣库存那条 `UPDATE ... JOIN` 里的 `g.sponsor_suspended = 0`**——
  `EnterpriseSponsorConcurrencyTest` 用裸 JDBC 事务先把商品置为不可用不提交，确定性地钉住「下单等它、提交后兑换失败」。另起一列而不是改成隐藏：恢复时分不清哪些是企业自己本来就隐藏的。
- **企业核销员**：V3 卷批已为 `mall_verifier.enterprise_id` 与核销判定留好位（企业作用域的核销员只能核销本企业赞助的商品，别家的码与「查无此单」同一句），这一批只是把「谁能指派」放给企业：按已实名志愿者手机号指派，一个志愿者同时只能是一处的核销员（唯一键），只能撤自己的。
- **企业积分账本**（V79，D5）：独立表、余额＝流水之和、不写 `point_record`。**入账不挂在核销那条语句上**——领取有三条路（现场核销 / 本人确认收货 / 系统自动确认，最后一条是一条批量 UPDATE），挂事件会漏掉批量那条，且 donate 不能反向依赖 enterprise；
  改由定时任务按领取时间回看窗口（默认 72 小时）补记，`uk_source(1, 兑换单 id)` 保幂等（几个补记同时跑每张单只记一次），窗口之外的用后台显式补记（`since` 必填，同证书补偿那一课：不设下界会让任务第一次跑就扫全部历史）。
  金额＝实际扣分减去抵扣快递费的积分（快递费不是企业的商品）；0 分不记（兑换卷全额抵扣的单）。**后台调整**（兑换企业权益时扣减）：幂等键 + 载荷复核（同志愿者账本），扣减按企业上锁（`lock:enterprise:points:`）防扣成负数——入账只会让余额变大，不必进锁。
- **企业看兑换单**：专门的 `SponsorOrderVO`，没有取货码（柜台上的持有者凭据）、没有收件信息、兑换人只留姓（字段集合由反射用例钉住）。
- 1 个权限点 `enterprise:points`（共 90）；代发布挂 `donate:goods`（它就是在发商品）。
- **没做的**：企业看自己商品的评价（商品评价 V3 已有，企业端入口留给赞助商评价段）；企业积分「兑换权益」的自助入口（Q：权益目录与价格需求没有，先由后台扣减）；企业核销员的核销记录单独列表（后台兑换单能看到核销人类型）。

### 爱心企业批·社区段 · 落地时定下的口径

- **企业帖不另建表**（V80 只给 `social_post` 加了作者类型 3 与两列快照）：帖子流、先发后审、关键词风控、举报、点赞评论、后台隐藏置顶删除全都跟着走一套。另起一张表等于把这些再写一遍，还要在帖子流里做两张表的合并分页。
- **作者名与头像存快照**：依赖方向是 `enterprise → social`，social 拿不到企业资料；快照顺带解决「企业改名之后老帖子显示成新名字」，与官方帖快照部门同一口径。
- ⚠️ **企业帖的 `author_id` 是企业 id，与志愿者 id 是两套自增序列**——凡是拿它去查志愿者的地方都会借用「id 恰好相同的那个志愿者」：作者卡片、发帖人的「一律禁止评论 / 点赞」设置、「这是我发的」（连带露出审核状态）、后台的真实姓名与学校、驳回的站内提示、互动记录。
  这一类缺陷靠随机数据撞不出来，`EnterprisePostReviewTest` 因此**显式插一个 id 恰好等于企业 id 的志愿者**，把「撞上」做成确定性的前提。
- **企业帖照样要有人审**：`SocialReviewService` 的待审队列与 `requirePending` 原本写死「只收志愿者帖」，不放行企业帖的话，先发后审的企业帖会永远停在待审核——这是写用例时当场撞出来的，不是设计时想到的。
- **企业没有关注关系与「不让TA看」**，所以企业帖不收可见性、一律公开；`SocialPostMapper.VISIBLE` 里企业那一支只有「后台没隐藏、没被驳回、没有命中关键词等着审」三条。
- **赞助商评价的资格只认兑换单**（donate 只读查询）：评的是这一次兑换的体验，没兑换过就没有可评的东西；一单一评靠生成列唯一键 `uk_active_order`（删掉之后可以重评），不靠先查再插。
- **屏蔽 ≠ 删除**：屏蔽是对外藏起来（作者与后台仍看得到、可恢复，评价人看得到屏蔽原因），删除是逻辑删除——Row 74 原文就是两个动作。公开列表不下发屏蔽状态。
- 1 个权限点 `enterprise:review`（共 91）。
- **没做的**：企业端看评价的回复（Row 74 没要求）；企业帖的「@TA」与私信（私信批）；企业主页的关注（企业不是关注关系里的一方）；**企业删自己帖子下的评论**——social 的「帖子作者可以删本帖评论」写死了只认志愿者作者（那条判断本来就挡着官方帖），要给企业开得另加入口，Row 15 F 没要求。

### 私信批 · 落地时定下的口径

- **会话按两人规范化**（`small_id` / `large_id` + `uk_pair`）：不规范化就会出现 (A,B) 与 (B,A) 两条，未读数与最后一条各记一半。并发对发的第一条消息靠 `INSERT IGNORE` + 读回赢家，不用「先查再插」。
- ⚠️ **发消息的事务第一条语句是「当前读锁住这条会话」**（`selectByIdForUpdate`）：陌生人限额是「先数一数再决定发不发」，不串行化的话同一个人 8 条同时发能成 5 条（`SocialChatConcurrencyTest` 当场撞出来的）。锁住之后，未读 / 已发计数与限额判定之间就没有窗口了。
- **未读数与已发条数记在会话上、用 `SET x = x + 1` 改**：逐会话去消息表 COUNT 在消息多了之后就是全表扫；而「查出来再写回去」会在并发对发时互相覆盖（压测的不变量专门盯这一条）。
- **清空聊天记录只抬高自己那一侧的水位**，消息行一条不删——Row 23 F 要的就是后台保存全部，让志愿者真删等于把追责依据交给被投诉的人处置。后台的查询因此**不看水位、也不看软删标记**（已删除的标出来）。
- **关键词命中不藏消息**：帖子是先藏后审，私聊藏起来等于单方面切断对话且双方都不知道（还会让对方以为你不理他）。命中的消息照常送达，另生成一条来源为「关键词」的工单**插队**进队列——「自动进入后台插队审核」说的是工单，不是拦截。
- **「禁止私信」与「不让TA看」报同一句话**：分开报等于告诉发信人「他把你拉黑了」。
- **禁言新增能力域 7「禁止私信」**，由 `COMMUNITY` 与 `ALL` 蕴含（承重条款 1）；**只挡发、不挡收**——收不到等于把对方的话也一起吞了。⚠️ 加能力域要同时改 `SanctionScope.assertKnown` 的上界，漏了那一档根本写不进库（这一批当场撞到）。
- **WebSocket 只用来收**（`/ws/social/chat?token=`）：发消息仍走 HTTP，落库、闸门、关键词、限额那一整套只写一份。握手用登录 token 认人，之后只信 session attributes 里的 id。**推送在事务提交之后做、失败只记日志**（D8「先落库后推送」）。
- 1 个权限点 `social:chat-view`（共 92），**默认不授任何人**，与 `social:real-name` 同一形状；处理私聊工单也挂它——不看内容就判不了，拆两个点等于让人盲审。
- **没做的**：撤回消息（Row 23 没要求）、群聊、消息已读回执（抖音那个界面也没有）、企业账号的私信（企业不是关注关系里的一方，也没有「主页搭建聊天通道」那条路径）。

### 系统治理批 · 落地时定下的口径

- **新建 `system` 模块而不是塞进 data**：data 是数据看板与投诉中心（业务聚合），而这一批是「平台自己的治理」——日志、配置、网盘。依赖只有 common / auth，拦截器注册在 api（「主动改变应用行为的配置放 api」）。
- **日志记什么**（Q8）：`/a/**` 的全部写操作 + **显式登记的敏感读**白名单（导出、志愿者详情、聊天记录、到家名单、证书下载、分享被打开、以及「谁翻了日志」）。全记 GET 会把日志刷满，真要追的那几条反而找不到；漏登记一条敏感读的后果是「谁看过」查不到，而那正是 Row 62 要解决的问题。
- **动作名取 `@Operation(summary)`**：那句话本来就是给人看的；另维护一份「动作名表」必然与端点漂开。**不记请求体**——改密码、重置密码那类请求体里就是密码本身。**失败也记**：被拒绝的越权尝试恰恰是追责时最要看的。
- **异步批量 + 队列满了丢弃 + 落库失败只记 ERROR**（D9）：写日志失败是小事，让写日志把业务请求拖住才是大事。领域测试没有 `@EnableScheduling`，用例直接调 `flush()`，断言因此是确定性的。
- ⚠️ **十位编号的两条语句必须在同一条连接上**：`LAST_INSERT_ID()` 是连接级的，`bumpNo` 与 `lastNo` 不包在事务里就各借一条连接，16 个线程同时取号只取到 2 个不同的号（并发用例当场撞出来的）。这是「一条语句读改写」之外的第二个前提，光有那条 SQL 不够。
- **文件网盘的授权沿文件夹往下继承**，只有超管能改授权；**看不到的整枝在树里不出现**（露出名字就等于露出了协会的目录结构）；删文件夹不连带删。
- **公开到小程序不往 `publicity_file` 同步**：同步就得靠定时任务把「到点开放」写成状态位，正是本项目反复避免的形状（名单公示、处置到期）。志愿者端另开 `GET /v/system/files`，窗口按时间现算；**关掉下载的只给名字不给地址**。
- **分享链接是随机令牌**，`GET /share/files/{token}` 与 `/callback/**` 同一机制落在鉴权处理器之外；「要不要登录」由那条分享自己的开关决定。
- **到家详细地址是字段级可见性**（Row 63）：没有 `activity:home-address` 的账号拿到的响应里根本没有地址与坐标——前端打码挡不住看响应体的人；判定在控制器，只有 HTTP 用例验得到。
- **没做的**：日志导出（Row 62 没要求，且导出本身又是一条要记的敏感读）；网盘的回收站与版本历史（Row 71 没要求）；编号段的后台维护入口（段由代码在第一次取号时建出来，`GET /a/system/serials` 只读）。

### 数据汇总批 · 落地时定下的口径

- **口径全部收在 owner 域的只读 service**，data 只组装（与看板、捐赠汇总同一条纪律）：散开就会在两个页面上显示两个数。
- ⚠️ **Row 79 的字面与系统里的概念对不上的地方，出参字段名与文档都写明**，不硬凑：
  「被封小组数」→ 系统里的动作是**解散**；「违规帖子数」→ 被驳回 ∪ 被后台隐藏（命中关键词还在排队的不算，那只是没审完）；
  「处罚数」→ 已通过的奖惩处罚单 + 社区禁言单；「已兑换」与「已发放」分成两个数（下单占住 vs 东西到手）。
- **系统里根本不记的东西给 null 不给 0**：相册的视频总数、查看人次、下载人数与人次（没有埋点），捐书的「修建书屋数」（V3 收尾批已有先例）。
  出参省略 null 字段，前端拿到的是「没有这个键」；给 0 会被读成「一次都没有」。
- **用例一律断言增量**并各配一个不该算进去的反例（游客不算注册、关键词待审不算违规、同一个人的两条违规帖只算一个人）。
- **没做的**：埋点（查看 / 下载人次要前端上报，属另一件事）；按时间区间的汇总（Row 79 没要求，现在给的是全量）。

## 五、跨批次承重条款

1. **限制只有一处事实来源。** 社区禁言扩展 `SanctionScope`，不另建表（D1）。
   ⚠️ 新增能力域时，`ALL` 与 `COMMUNITY` 的**蕴含关系**必须同步——否则「拒绝使用」反而管得比「禁言」少（V32 那一课）。
2. **命名**：权限点按模块（`social:` / `enterprise:` / `org:` / `user:` / `sys:`），表名按聚合根概念
   （`social_post_*` / `enterprise_*` / `org_form_*` / `org_exam_*`）——同 V3 承重条款 2 的判据。
3. **积分**：相册积分分配新码 `ALBUM=7`（非消费）；企业积分**独立账本、不写 `point_record`**（D5）。
4. **未成年人数据**：社区帖子 / 私信 / 相册都可能出现未成年人影像与信息。
   **后台看真实姓名与学校仅最高权限**（Row 23 F 原文），私信查看权默认不授任何人（D8）。
5. **锁与测试纪律**：同 V3 承重条款 5——并发用例 `Future.get()`、真并发时序、显式 RR、变异验证、
   **选锁按「读完之后改不改这一行」**。社区计数（点赞 / 关注）用唯一键防重 + 计数列 CAS，**不在 Java 里先查后插**。
6. **通知**：只走 `SmsNotifyService` / `NotificationService`；**用户的通知偏好**（Row 48「订阅通知：用户可自主选择关闭或打开某个内容的提醒」）
   在 `SmsNotifyService` 的收件人解析处**统一过滤**，验证码等交易类通知不可关闭——
   **不让每个业务调用方各自判断偏好**（散开就会有人漏掉且没有征兆，同 `listNotifiablePhones` 那条）。
7. **部署侧改动要写进 `部署/`**：私信的 nginx `Upgrade`/`Connection` 头、视频上传的 `client_max_body_size`
   （或改前端直传 TOS）——**两个 server 块都要改**（`nginx.conf` 与 `nginx-xcx-api.conf` 的 per-server 教训）。
8. **一句风险陈述**：V4 结束时无界面可达的后端端点将再增加约 120 个。这是「仅后端」交付形态的直接结果。

## 七、模块与依赖

```
social     → common / auth（志愿者只读 + 处置闸门）/ organization（官方帖的部门）
enterprise → common / auth / donate（商品、核销员、订单事件）/ social（企业发帖）
organization（问卷引擎 + 考试） → common / auth              ← 不新增依赖方向
activity（相册） → social（同步发帖）                          ← ⚠️ 新方向，见下
data → 各域只读 stats 服务
```

⚠️ **相册同步社区不能让 activity 依赖 social**：social 若日后要读活动信息（官方帖显示「报名或分队名称」，Row 23 C）
就会成环。故相册批**发事件**（`AlbumPhotosApprovedEvent`，同 `AttendanceConfirmedEvent` 的形状），
social 监听并发帖——依赖方向 social → activity，与既有 honor → activity 同向。
⚠️ 事件不持久（`CertificateReconcileJob` 那一课）：同步社区失败只是「少一条帖子」，
**不做补偿任务**是可接受的——但要在监听器里记 ERROR，而不是 catch 后无声吞掉。
