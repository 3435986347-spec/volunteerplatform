## 三、结构性问题

1. **历史与现状混写。** 大部分段落是「先这样做 → 撞出问题 → 改成那样 → 某次评审又补了一条」的叙事。这对理解「为什么」很有价值，
   但 agent 要读完整段才知道现在的规则是什么，而且容易把中间某一步当成现行做法。
2. **同一事实写在多处、版本不一。** 权限点总数、迁移清单、部门分工都是。手写的数字每批都要同步，漏一处就互相矛盾。
3. **协会决策没有统一编号、散在 6 份文件。** 同一条口径（如禁用账号能不能申诉）改过两次，只有把几份回执串起来看才知道为什么。
4. **接口按版本切（v1~v4），不按领域。** 想知道「捐赠相关的全部端点」要翻四份文档。
5. **跨仓库断开。** 小程序、控制台的 agent 看不到后端口径；控制台的组件坑（`PageHead.actions`、`Tag` 只认 `color`、开关在表单项里会被拉成方块）只记在后端仓库的 CLAUDE.md 里。
6. **需求原件是二进制。** 引用了 41 个不同的 PRD Row，但 Row 的原文 agent 直接读不到。
7. **踩坑记录有价值但难复用。** 「CAS 失败后的复核要当前读」「别锁不存在的行」「AFTER_COMMIT 里写库」「webhook 不能返回 String」这类套路散在各模块行里，同一课在不同批次重复写了好几遍。

## 四、要不要按领域拆、怎么路由

**结论：按领域拆，但路由的键用「业务领域」，不用 Maven 模块；再加一层按代码目录自动加载的模块说明。**

理由：任务、需求表、协会答复都是用业务语言说的（「积分」「证书」「微心愿」），不是「donate 模块」；
而业务领域和模块并不一一对应——积分账本在 activity、商城在 donate、企业积分在 enterprise；处置闸门的表在 auth、开单在 honor、闸门挂在 activity 和 social 上。
只按模块拆，问「积分怎么算」的 agent 要自己知道去四个模块里找。

### 两层结构

| 层 | 放在哪 | 管什么 | 何时被读 |
|---|---|---|---|
| **领域页** | `知识库/领域/*.md`（文档仓库） | 业务规则、协会决策、PRD Row、对外接口、已知限制与待办 | 根路由表指过去，按需读 |
| **模块说明** | `代码/hengde-volunteer-*/CLAUDE.md`（后端仓库） | 这个模块的代码不变式、关键类与承重测试、只属于这段代码的坑 | Claude Code 动到这个目录时**自动加载** |

两层互相链接，不复制内容：一条事实只有一个归属页，其他地方只放链接。

### 领域划分（沿用 `业务领域划分.md` 的 12 个，按现状映射到模块）

| 领域 | 主要模块 | 也涉及 |
|---|---|---|
| 一 用户与身份认证 | auth | user（资料）、api（鉴权闸门） |
| 二 志愿活动 | activity | organization（临时负责人）、honor（活动证书） |
| 三 积分体系 | activity（账本） | donate（商城、卷）、enterprise（企业积分）、honor（排行） |
| 四 公益捐赠（众筹 / 捐书 / 结对 / 微心愿） | donate | trade（收付）、honor（捐赠证书） |
| 五 组织管理 | organization | auth（管理团队标记） |
| 六 爱心企业 | enterprise | donate（赞助商品）、social（企业帖） |
| 七 社区交流 | social | auth（处置能力域） |
| 八 荣誉展示（排行 / 勋章 / 证书 / 奖惩） | honor | auth（处置表）、activity、donate |
| 九 信息与公示 | publicity | activity（名单公示）、system（内置文件） |
| 十 个人中心 | user | auth（注销、订阅偏好） |
| 十一 后台管理系统 | organization（RBAC）、system、data | 各域的 `/a` 端点 |
| 十二 监管后台（SaaS） | 未建 | — |

### 横切主题单独成页（不硬塞进某个领域）

积分账本 · 证书（活动 + 捐赠）· 处置闸门 · 通知短信 · 收付与退款 · 文件上传与「本系统上传」判定 · 鉴权与三套登录态 ·
并发与锁的套路 · 测试纪律（变异验证、赛跑用例、Testcontainers）· 迁移规则（挑号、一文件一条有失败可能的语句）· 部署与配置。

### 路由表（根 CLAUDE.md 里只放这个 + 硬规矩）

一张「触发词 → 该读的页」表。触发词用 agent 在任务里最可能看到的几种写法：

- 业务词：积分、证书、微心愿、兑换、禁言……
- 需求表 Row 号：Row 41 → 荣誉展示 / 奖惩
- 协会条目号：乙-5 → 积分体系 / 商城
- 权限点前缀：`donate:*`、`honor:*`
- 模块名与 URL 前缀：`/v/donate/**` → 公益捐赠 / 积分体系

### 每个领域页的固定结构

1. 现行规则（只写现在是什么，一条一句，带承重测试名）
2. 关键代码（类 / 表 / 迁移号）
3. 接口（链到契约核对过的 URL 文档对应段落）
4. 决策记录（统一编号：日期、问题、协会原话、我们的决定、落点、推翻了哪条）
5. 已知限制与待办（含外部依赖：商户号、样本 PDF……）
6. 历史（只放链接，指向变更日志）

## 五、建议的执行顺序

1. **先修第二节的过期事实**（小改动，马上降低误导）。
2. **把 CLAUDE.md「已完成」表的 14 行机械下沉**到各模块的 `CLAUDE.md`：现状在前，历史叙事挪到变更日志。根文件目标 1 万字符以内。
3. **建领域页 12 + 横切页约 10**：从规划、回执、URL 文档、模块行里抽现行规则；每条事实只写在一个页里。
4. **决策记录统一编号**：回执一~五 + 规划里的自定口径合成一份，按领域分组。
5. **需求原件转 markdown**：xlsx 按 Row 一行一段（含前端信息 / 备注 / 后端要求 / 原型页码），PDF 按页抽文字。
6. **可推导的事实用脚本生成并校验**：权限点表、迁移表、按领域的接口索引；把 `verify_url_contract.py` 的思路扩到知识库（数字对不上就报错）。
7. **清理**：删 `v1/admin.md`、`v1/volunteer.md`、`v1/已完成功能清单.md`；归档 docx 与冻结的附录。
8. **小程序、控制台仓库各加一份短 CLAUDE.md**（+ 给其他 agent 的 `AGENTS.md`），指向知识库对应页。
9. **把维护写进收尾清单**：每批结束时更新领域页的决策与现行规则、模块 CLAUDE.md、变更日志。

⚠️ 文档仓库推到 GitHub：涉及线上安全状况的材料（如未提交的《线上升级核对》）不进知识库。
