# 发版操作手册（后端 jar + 后台控制台）

> **适用**：服务器已经按 `文档/v1/部署说明.md` 装过一次（systemd 服务、nginx、`/etc/hengde/api.env` 都在），现在是**更新**。第一次装机请看那份。
>
> 全文分「**本机**」（你的 Mac）和「**服务器**」两种终端，每段命令前都标了在哪跑。按顺序做，**第 3 步备份不能跳**。

---

## 这一次（2026-10-17）的特殊情况，先看

| 情况 | 影响 | 本手册怎么处理 |
|---|---|---|
| 线上 `/api/actuator/info` 返回 **500** | 服务器跑的是 10-08 之前的旧包，这次要从九月**一口气跑几十条迁移到 V100**，首启会比平时慢 | 第 3 步先备份库；第 5 步迁移期间**不要重启** |
| 新 jar 版本号**还是 2.0.1**，而服务器上已经有一个 2.0.1 | 原名 `cp` 上去会**把旧包盖掉，回滚就没了** | 上传时改名为 `…-2.0.1-20261017.jar`（服务只认软链，文件名随便取，不用重新打包） |
| 控制台的 `assets/` 在 Mac 上是 `700` 权限，16 个文件是 `-rwx------` | 原样解到服务器上，nginx 读不了，**所有 JS 403，整个后台白屏** | 第 7 步解包后统一改成 755/644，再用 curl 验证 |
| 仓库里 `index.html` 的高德 key 是**空的** | 如果服务器上的 `index.html` 手工填过 key，直接覆盖会让**地图选点失效** | 第 7 步覆盖前先抄下来，覆盖后填回去 |

本次 jar（已核对）：`build.time=2026-10-17T07:15:17Z`，迁移到 **V100**，13 个领域模块都打进去了。

> ⚠️ 这次部署会把 V2–V4 的出参变化一起带上线（比如几个 `/v` 列表从数组改成了分页对象）。**发之前跟小程序那边确认一句**：线上那版小程序接的是不是真后端、能不能吃这次的出参。

## 第 0 步：设两个变量（本机）

```bash
SERVER=root@118.145.69.25     # 换成你实际 ssh 登录用的账号
TAG=20261017                  # 本次发版的标记，用在文件名里
```

> 这两个变量只在当前这个终端窗口里有效。中途新开了终端要重新设一遍。

## 第 1 步：本机核对、打包、上传

### 1.1 核对 jar 是新的

```bash
cd ~/Desktop/volunteerplatform/代码
J=hengde-volunteer-api/target/hengde-volunteer-api-2.0.1.jar
unzip -p $J META-INF/build-info.properties | grep -E 'version|time'
unzip -l $J 'BOOT-INF/lib/hengde-volunteer-*' | grep -c 'BOOT-INF/lib/hengde-volunteer-'
```

应看到 `build.time=2026-10-17T07:15:17…`，第二行输出 **13**。少了就说明构建时漏了模块，别往下走（重新 `./mvnw -o -q clean install -DskipTests`，核对 Reactor Summary 列满 15 行）。

### 1.2 打包后台页面（只要 `index.html` + `assets/`）

```bash
cd ~/Desktop/volunteerplatform-back
git status --short
```

**这一行应该没有任何输出**——只发已经提交的代码。有输出就先处理掉（提交或撤销）。

```bash
COPYFILE_DISABLE=1 tar czf /tmp/admin-web-$TAG.tgz --exclude='.DS_Store' --exclude='* 2*' index.html assets
tar tzf /tmp/admin-web-$TAG.tgz | wc -l
```

- `COPYFILE_DISABLE=1`：不让 macOS 往包里塞 `._xxx` 隐藏文件。
- `--exclude='* 2*'`：排除 iCloud 生成的「api 2.js」这类冲突副本。
- 第二行应输出 40 多（目录 + 文件数）。`tests/`、`uploads/`、`AGENTS.md` 等都**不在包里**，这是对的。

### 1.3 传到服务器的 /tmp

```bash
scp ~/Desktop/volunteerplatform/代码/hengde-volunteer-api/target/hengde-volunteer-api-2.0.1.jar \
    $SERVER:/tmp/hengde-volunteer-api-2.0.1-$TAG.jar
scp /tmp/admin-web-$TAG.tgz $SERVER:/tmp/
scp ~/Desktop/volunteerplatform/部署/api.env.example $SERVER:/tmp/
```

jar 有 170 MB，第一条要等一会儿。注意 jar 在**上传时就改了名**（带 `-$TAG`）。

## 第 2 步：登上服务器，先确认实际路径

```bash
ssh $SERVER
```

以下全部在**服务器**上执行。先把变量再设一遍：

```bash
TAG=20261017
```

确认服务和目录跟本手册写的一致：

```bash
systemctl cat hengde-api | grep -E 'WorkingDirectory|EnvironmentFile|ExecStart'
ls -l /opt/hengde/api/
ls -ld /opt/hengde/admin-web
```

期望看到：

- `ExecStart=… -jar /opt/hengde/api/hengde-volunteer-api.jar …`（**指向软链**，不是带版本号的文件）
- `ls -l` 里 `hengde-volunteer-api.jar -> hengde-volunteer-api-xxx.jar`，**把箭头后面那个旧文件名记下来**，回滚要用

> 对不上怎么办：
> - `ExecStart` 直接写着 `hengde-volunteer-api-2.0.1.jar`（没有软链）——那是更早的装法，先按 `文档/v1/部署说明.md` 第 6 节最后一条把服务单元换成软链版，再继续。
> - 目录不是 `/opt/hengde/...`——下文所有路径照你服务器上的实际路径改。

## 第 3 步：备份（必做）

**Flyway 不会自动回滚。** 这次要跑几十条迁移，任何一条出问题都只能靠这份备份恢复。

```bash
sudo grep -E '^DB_USER=' /etc/hengde/api.env
mysqldump -u hengde -p --single-transaction --routines --set-gtid-purged=OFF hengde_volunteer | gzip > ~/hengde_$TAG.sql.gz
```

- `-u` 后面换成上一行查出来的 `DB_USER`；密码在提示时输入（就是 `api.env` 里的 `DB_PWD`），**别写在命令行上**，会留在 history 里。
- MySQL 不在本机的，加 `-h <主机>`。用的是 MariaDB 的，去掉 `--set-gtid-purged=OFF`。

验证备份完整：

```bash
ls -lh ~/hengde_$TAG.sql.gz
zcat ~/hengde_$TAG.sql.gz | tail -1
```

最后一行应是 `-- Dump completed on …`。**没有这行就说明备份没导完，不要往下走。**

## 第 4 步：核对环境变量有没有漏

九月之后环境变量模板改过三次。下面这几行只比较**变量名**（不读值），列出「模板里有、服务器上没有」的：

```bash
grep -oE '^[A-Z][A-Z0-9_]*=' /tmp/api.env.example | sort -u > /tmp/k.tpl
sudo grep -oE '^[A-Z][A-Z0-9_]*=' /etc/hengde/api.env | sort -u > /tmp/k.srv
comm -23 /tmp/k.tpl /tmp/k.srv
rm -f /tmp/k.tpl /tmp/k.srv
```

对每个列出来的变量，去 `/tmp/api.env.example` 里找它上方的注释：

- 段标题带 **✅** 的（profile、数据库、PII 密钥、超管密码、小程序、短信、对象存储、协议）——**必须补**，不补启动会被守卫拦下；
- 其余都有默认值，不填就用默认，可以不管。

> 本次已核对过：九月之后新增的微信支付、快递100 推送默认都是**关**的，九月的 `api.env` 照样能过守卫。这一步主要是防万一。

要补就编辑：

```bash
sudo vi /etc/hengde/api.env
```

⚠️ 这个文件是 systemd 读的，**值后面不能跟注释**：`KEY=xxx  # 说明` 会把 `  # 说明` 当成值的一部分，而且不会报错。注释只能单独占一行。

## 第 5 步：换后端

```bash
sudo cp /tmp/hengde-volunteer-api-2.0.1-$TAG.jar /opt/hengde/api/
sudo ln -sfn hengde-volunteer-api-2.0.1-$TAG.jar /opt/hengde/api/hengde-volunteer-api.jar
ls -l /opt/hengde/api/hengde-volunteer-api.jar
```

确认箭头指向带 `-20261017` 的新文件，然后重启并看日志：

```bash
sudo systemctl restart hengde-api
sudo journalctl -u hengde-api -f
```

按顺序应该依次出现（`Ctrl+C` 退出跟踪，服务不受影响）：

1. `生产配置守卫校验通过`
2. `Migrating schema … to version "…"` ——**会一条一条刷几十行，这时候别动它**
3. `Successfully applied N migrations … now at version v100`
4. `Tomcat started on port 8080 … with context path '/api'`

### 出问题时

| 日志里看到 | 怎么办 |
|---|---|
| 守卫列出一串问题 | 照着补 `/etc/hengde/api.env`，然后 `sudo systemctl restart hengde-api`。这时还没动库，放心改 |
| 某条迁移报错（`Migration V… failed`） | **立刻** `sudo systemctl stop hengde-api`——服务配了失败自动重启，不停的话它会每 5 秒撞一次。记下是哪个 V 号、报的什么错，然后走文末「回滚」。**不要自己跑 `flyway repair`** |
| 迁移跑到一半 ssh 断了 | 没关系，服务在服务器上继续跑。重新 ssh 上来接着看日志即可，**不要因为断线去重启服务** |

## 第 6 步：确认跑的是新包

```bash
curl -s http://127.0.0.1:8080/api/actuator/info; echo
```

两样都对才算成功：

- `"time":"2026-10-17T07:15:17.171Z"`（构建时间，UTC）
- `"schemaVersion":"100"`

> 这一步不能省：版本号前后都是 2.0.1，日志里的 `Starting … v2.0.1` 分不出新旧。软链没指对时 restart 照样成功，跑的却是旧代码，**不会有任何报错**。只有 `build.time` 能分辨。

## 第 7 步：换后台页面

### 7.1 先抄下服务器上的高德配置

```bash
grep -n "__AMAP_" /opt/hengde/admin-web/index.html | grep "||"
```

会看到三行，形如 `window.__AMAP_KEY__ = window.__AMAP_KEY__ || '…';`。**如果引号里有值**，把这三行抄在本地（别贴进聊天、别提交进 git），7.3 要填回去。三行引号里都是空的就跳过。

### 7.2 解包到新目录、修权限

```bash
sudo rm -rf /opt/hengde/admin-web.new
sudo mkdir -p /opt/hengde/admin-web.new
sudo tar xzf /tmp/admin-web-$TAG.tgz -C /opt/hengde/admin-web.new --no-same-owner
sudo find /opt/hengde/admin-web.new -type d -exec chmod 755 {} +
sudo find /opt/hengde/admin-web.new -type f -exec chmod 644 {} +
```

- 解包时出现 `Ignoring unknown extended header keyword` 的警告，无害（是 macOS tar 带的元数据）。
- **后两行不能省**：Mac 上 `assets/` 是 700 权限，不改的话 nginx 读不了。

### 7.3 填回高德配置（7.1 有值才需要）

```bash
sudo vi /opt/hengde/admin-web.new/index.html
```

找到那三行，把引号里的值填回去。

### 7.4 切换（旧目录留作备份）

```bash
sudo mv /opt/hengde/admin-web /opt/hengde/admin-web.bak-$TAG
sudo mv /opt/hengde/admin-web.new /opt/hengde/admin-web
```

**nginx 不用重启**——已配协商缓存，浏览器下次请求就拿到新文件。

### 7.5 先用 curl 验，再开浏览器

```bash
curl -sI http://118.145.69.25/assets/api.js | head -1
curl -s  http://118.145.69.25/ | grep -c 'assets/page-'
```

- 第一行必须是 `HTTP/1.1 200 OK`。**是 403 就是权限没改对**，回 7.2 重跑那两行 `chmod`（目录已经 mv 过了，路径改成 `/opt/hengde/admin-web`）。
- 第二行是页面脚本的数量，应该是**几十**；只有个位数说明拷上去的还是旧的 `index.html`。

## 第 8 步（一次性，建议做）：给私信补 WebSocket

这个包里有 V4 私信。小程序连的是 `xcx.hdzyz.com.cn`，那份 nginx 配置**还没放行 WebSocket**——不补的话私信照样能发（消息落库），但对方要**刷新才看得到**，很容易被当成前端 bug。

先看有没有加过：

```bash
sudo grep -n "api/ws" /etc/nginx/conf.d/*.conf
```

有输出就跳过本步。没有就编辑小程序那份配置：

```bash
sudo vi /etc/nginx/conf.d/xcx.hdzyz.conf
```

在 `listen 443` 那个 `server { }` 里、`location / {` **前面**加：

```nginx
    location /api/ws/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_read_timeout 300s;     # 默认 60s 会把闲着的长连接掐断
        access_log off;              # 握手 token 在查询串里，别写进访问日志
    }
```

校验再生效（**`nginx -t` 不通过就别 reload**，改回去）：

```bash
sudo nginx -t && sudo systemctl reload nginx
```

## 回滚

### 只回滚后台页面（后端没问题时）

```bash
sudo rm -rf /opt/hengde/admin-web
sudo mv /opt/hengde/admin-web.bak-$TAG /opt/hengde/admin-web
```

### 回滚后端

⚠️ **新包已经跑过迁移，表结构变了，旧包跑在新表上会出错——必须连库一起恢复。** 恢复会丢掉备份之后写进去的所有数据，所以发现问题要尽早决定。

```bash
sudo systemctl stop hengde-api

# 1) 删库重建再导入。不能直接往现有库里导：迁移新建的那些表不在备份里，
#    会留下来，下次再升级时迁移会撞「表已存在」而失败。
mysql -u hengde -p -e "DROP DATABASE hengde_volunteer; CREATE DATABASE hengde_volunteer DEFAULT CHARACTER SET utf8mb4;"
gunzip < ~/hengde_$TAG.sql.gz | mysql -u hengde -p hengde_volunteer

# 2) 软链指回旧包（文件名是第 2 步记下的那个）
sudo ln -sfn <旧jar文件名> /opt/hengde/api/hengde-volunteer-api.jar
sudo systemctl start hengde-api
sudo journalctl -u hengde-api -f
```

后台页面也一起回滚（见上一小节）——新页面会调用旧后端没有的接口。

## 附：下次发版前

- **先升版本号再打包**，就不用像这次一样靠改文件名区分：
  ```bash
  cd ~/Desktop/volunteerplatform/代码/hengde-volunteer-parent
  ./mvnw versions:set -DnewVersion=2.0.2 -DgenerateBackupPoms=false
  ./mvnw -o -q clean install -DskipTests
  ```
  打出来就是 `hengde-volunteer-api-2.0.2.jar`，日志里的版本号也能直接分辨新旧。
- 构建**一律带 `clean`**（仓库在 iCloud 桌面上，`target/` 里会冒「X 2.class」冲突副本）。
- 改了 `部署/nginx.conf` 或 `部署/nginx-xcx-api.conf` 时，把它传到服务器 `/tmp` 后先 `diff` 再决定怎么合——服务器上的配置可能有本地没有的改动，**别整份覆盖**：
  ```bash
  sudo diff /etc/nginx/conf.d/hengde-admin.conf /tmp/nginx.conf
  ```
